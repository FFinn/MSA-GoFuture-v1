# ADR-004: Многотенантная платформа GoFuture для партнёров

**Статус:** На рассмотрении  
**Автор:** Александр Вафин  
**Заинтересованные стороны:** продуктовые команды GoFuture, платформенная команда, SRE-команда, информационная безопасность, команда сопровождения партнёров, архитектурный комитет  
**Дата:** 2026-09-15

---

## 1. Контекст

GoFuture должен быстро подключать партнёров в новых регионах и при этом не допускать смешения их данных. Партнёром может быть локальный сервис такси, банк, маркетплейс или другая компания, которая использует платформу GoFuture под своим брендом и с собственным набором интеграций.

Предыдущие архитектурные решения уже задали основу платформы:

- восемь доменных сервисов: Booking, Driver, Pricing, Payments, Notification, Geography, Analytics и Fraud;
- отдельное владение данными каждого домена;
- событийный обмен через Apache Kafka;
- потоковую обработку Apache Flink;
- глобальное развёртывание в нескольких регионах;
- региональный шлюз программного интерфейса;
- единый контур наблюдаемости на Prometheus, Grafana, Loki, OpenTelemetry и Jaeger.

Многотенантность должна дополнять эту архитектуру, а не создавать отдельную ветку кода для каждого партнёра. Основная задача — ввести устойчивый контекст партнёра, изолировать его данные и доступ, автоматизировать создание окружения и позволить менять функции через конфигурацию.

## 2. Требования

### 2.1. Функциональные требования

| № | Требование |
|---|---|
| **ФТ-01** | Для каждого партнёра должен существовать уникальный `tenant_id`, который используется во всех сервисах и событиях. |
| **ФТ-02** | Данные одного партнёра не должны быть доступны пользователям, сервисным учётным записям и процессам другого партнёра. |
| **ФТ-03** | Административные пользователи партнёра должны входить через единый вход (SSO) с поддержкой OIDC или SAML. |
| **ФТ-04** | Права пользователей должны определяться ролями и областью доступа конкретного партнёра. |
| **ФТ-05** | Подключение нового партнёра должно выполняться автоматически по одному процессу без ручного создания баз, секретов, ролей, топиков и панелей мониторинга. |
| **ФТ-06** | Партнёр должен получать собственную конфигурацию функций: доступные тарифы, интеграции, ограничения, оформление и включённые возможности. |
| **ФТ-07** | События Kafka должны сохранять принадлежность конкретному партнёру и не смешиваться с событиями других партнёров. |
| **ФТ-08** | Мониторинг должен позволять видеть состояние платформы как по всем партнёрам, так и по отдельному `tenant_id`. |
| **ФТ-09** | GoFuture должен иметь контролируемый аварийный доступ к окружению партнёра только по отдельной процедуре с полным аудитом. |
| **ФТ-10** | Партнёр должен иметь возможность использовать собственный корпоративный поставщик идентификации без изменения прикладных сервисов GoFuture. |

### 2.2. Нефункциональные требования

| № | Категория | Требование | Критичность |
|---|---|---|---|
| **НФТ-01** | Изоляция | В рабочих таблицах не должно быть смешения строк разных партнёров. Для каждого партнёра создаются отдельные логические базы данных каждого домена. | Критичная |
| **НФТ-02** | Безопасность | `tenant_id` нельзя принимать как доверенное значение из заголовка, строки запроса или тела клиентского запроса. Контекст партнёра определяется из проверенного токена. | Критичная |
| **НФТ-03** | Масштабирование | Нагрузка одного партнёра не должна блокировать остальных; для партнёрских контуров применяются независимые квоты и ограничения ресурсов. | Критичная |
| **НФТ-04** | Поддерживаемость | Кастомизация выполняется настройками, флагами возможностей и адаптерами интеграций без создания отдельной ветки исходного кода партнёра. | Высокая |
| **НФТ-05** | Наблюдаемость | Метрики, журналы и трассы должны содержать контекст партнёра, но не создавать неконтролируемую кардинальность. | Высокая |
| **НФТ-06** | Аудит | Изменение ролей, конфигурации, секретов и аварийный доступ должны фиксироваться в неизменяемом журнале аудита. | Критичная |
| **НФТ-07** | Региональность | При подключении партнёра указываются разрешённые регионы и юрисдикция данных; процесс создания окружения не должен нарушать правила размещения данных из предыдущего архитектурного решения. | Критичная |
| **НФТ-08** | Автоматизация | Повторный запуск шага подключения должен быть идемпотентным и не создавать дубликаты окружений, ролей, баз и топиков. | Высокая |

## 3. Решение

### 3.1. Общая модель

Выбирается модель **общего управляющего контура и изолированных партнёрских ячеек**.

Управляющий контур отвечает за:

- реестр партнёров;
- управление идентификацией и доступом;
- конфигурацию партнёров;
- автоматическое создание окружений;
- общую наблюдаемость;
- аудит административных действий.

Для каждого партнёра создаётся отдельная логическая ячейка внутри разрешённого регионального контура. Ячейка не означает обязательный отдельный физический кластер Kubernetes. По умолчанию это отдельное пространство имён в региональном GKE с собственными сервисными учётными записями, сетевыми политиками, квотами, секретами и хранилищами.

Если нормативные требования или нагрузка конкретного партнёра требуют физического разделения, тот же шаблон разворачивается в выделенном кластере без изменения прикладной модели.

Диаграмма верхнего уровня: [`C2-multitenant-platform.puml`](./C2-multitenant-platform.puml).

### 3.2. Идентификатор партнёра

Каждому партнёру присваивается неизменяемый `tenant_id`, например `bank-a` или `taxi-partner-17`.

`tenant_id` используется:

- в реестре партнёров;
- в токене пользователя и сервисной учётной записи;
- в конфигурации шлюза программного интерфейса;
- в именах партнёрских Kafka-топиков и групп потребителей;
- в атрибутах трассировки;
- в метриках ограниченной кардинальности;
- в журналах аудита;
- в привязке к отдельным доменным базам.

Клиент не может самостоятельно выбрать `tenant_id`. Шлюз проверяет подпись и издателя токена, извлекает принадлежность к партнёру из доверенных утверждений токена и передаёт внутренний контекст дальше. При несовпадении партнёра в маршруте, токене и реестре запрос отклоняется.

### 3.3. Изоляция вычислительного контура

Для каждого партнёра создаётся отдельное пространство имён Kubernetes:

`tenant-<tenant_id>`.

В нём задаются:

- отдельная сервисная учётная запись;
- `ResourceQuota` и `LimitRange`;
- сетевые политики по принципу запрета по умолчанию;
- ссылки только на секреты этого партнёра;
- конфигурация включённых возможностей;
- разрешённые интеграции;
- при необходимости отдельные экземпляры сервисов, которым требуется независимое масштабирование.

Базовые образы сервисов остаются общими для всех партнёров. Отличия задаются конфигурацией, а не копированием исходного кода.

### 3.4. Изоляция данных

Для выполнения требования полной изоляции данных не используется одна общая таблица с колонкой `tenant_id`.

Для каждого партнёра создаются отдельные логические базы PostgreSQL по доменам:

- `<tenant_id>_booking`;
- `<tenant_id>_driver`;
- `<tenant_id>_geography`;
- `<tenant_id>_pricing`;
- `<tenant_id>_payments`;
- `<tenant_id>_fraud`;
- `<tenant_id>_notification`.

Физически несколько таких баз могут размещаться на одном управляемом кластере PostgreSQL, если это допускается требованиями партнёра. Изоляция обеспечивается отдельными базами, отдельными пользователями базы и отдельными секретами. Сервисная учётная запись одного партнёра не получает учётные данные баз другого партнёра.

Для оперативных хранилищ используется тот же принцип:

- отдельный логический экземпляр или отдельная область Redis с отдельными учётными данными;
- отдельный индекс Elasticsearch Geography;
- отдельные префиксы объектного хранилища, если оно используется доменом.

Для партнёров с повышенными требованиями доступен выделенный экземпляр хранилища. Это меняет стоимость, но не меняет прикладную архитектуру.

### 3.5. Изоляция событий Kafka

Региональное разделение из событийной архитектуры сохраняется. Для партнёрских событий имя топика расширяется идентификатором партнёра:

`gofuture.<region>.<tenant_id>.<domain>.<stream>.v1`.

Примеры:

- `gofuture.sg.bank-a.booking.events.v1`;
- `gofuture.sg.bank-a.payments.events.v1`;
- `gofuture.jkt.taxi-partner-17.driver.location.v1`.

Для каждого партнёра автоматически создаются:

- необходимые топики;
- группы потребителей;
- права Kafka ACL;
- топики повторной обработки;
- топики недоставленных сообщений.

Сервисная учётная запись партнёра получает права только на его пространство топиков. Общеплатформенные технические события при необходимости остаются в отдельных системных топиках без пользовательских данных партнёров.

### 3.6. Конфигурация и кастомизация

Создаётся **Сервис конфигурации партнёров**. Он хранит:

- включённые возможности;
- ограничения по продуктам;
- правила брендирования;
- разрешённые платёжные и картографические поставщики;
- ссылки на секреты интеграций;
- региональные параметры;
- квоты;
- версии конфигурации.

Для изменения поведения используются флаги возможностей и конфигурационные параметры. Например, один партнёр может использовать локальный платёжный шлюз и собственный картографический сервис, другой — стандартные интеграции GoFuture.

Если требуется новая бизнес-функция, сначала оценивается возможность сделать её общей настраиваемой возможностью. Создание отдельной ветки кода под конкретного партнёра считается нежелательным решением, поскольку оно быстро приведёт к расхождению версий платформы.

## 4. Управление идентификацией и доступом

### 4.1. Выбор IAM

Для административного и партнёрского доступа выбирается **Keycloak**.

Причины выбора:

- поддержка OpenID Connect и SAML;
- федерация с внешними поставщиками идентификации;
- ролевой доступ;
- отдельные области безопасности для партнёров;
- возможность развёртывания в собственной инфраструктуре;
- отсутствие зависимости прикладных сервисов от конкретного корпоративного каталога партнёра.

Для каждого партнёра создаётся отдельный `realm`. Это даёт независимые:

- пользователей;
- группы;
- роли;
- приложения-клиенты;
- настройки срока жизни токенов;
- федерацию с корпоративным поставщиком идентификации партнёра.

Управляющие пользователи GoFuture находятся в отдельном служебном `realm` и не получают автоматического доступа к данным партнёров.

### 4.2. Единый вход

Если у партнёра есть собственный поставщик идентификации, его `realm` связывается с ним по OIDC или SAML.

Путь входа:

1. пользователь открывает портал партнёра;
2. Keycloak определяет нужный `realm` по партнёру;
3. пользователь перенаправляется к корпоративному поставщику идентификации партнёра;
4. после успешной аутентификации Keycloak выпускает токен GoFuture;
5. токен содержит `tenant_id`, роли и область доступа;
6. шлюз программного интерфейса проверяет токен и формирует внутренний контекст партнёра.

Пользователю одного `realm` нельзя назначить роль другого партнёра.

### 4.3. Ролевой доступ

Роли и уровни доступа приведены в [`roles-access.md`](./roles-access.md).

Права проверяются на двух уровнях:

1. шлюз отсекает запросы без требуемой области доступа;
2. доменный сервис проверяет право на конкретную бизнес-операцию.

Наличие роли не отменяет изоляцию партнёра: пользователь с ролью администратора партнёра A не может передать `tenant_id` партнёра B и получить его данные.

### 4.4. Аварийный доступ GoFuture

Для поддержки критического инцидента предусматривается отдельная процедура временного доступа:

- постоянного межпартнёрского доступа у сотрудников GoFuture нет;
- доступ выдаётся на ограниченное время;
- требуется подтверждение ответственного лица;
- назначается конкретный партнёр и конкретная причина;
- все действия пишутся в журнал аудита;
- после истечения времени роль отзывается автоматически.

## 5. Автоматическое подключение нового партнёра

Подробный поток показан на [`C3-partner-provisioning.puml`](./C3-partner-provisioning.puml).

Создаётся **Сервис управления партнёрами**, который хранит состояние подключения и запускает идемпотентный процесс подготовки окружения.

### 5.1. Состояния подключения

Партнёр проходит состояния:

`DRAFT → VALIDATING → PROVISIONING → VERIFYING → ACTIVE`.

При ошибке процесс переходит в `FAILED`, при этом уже выполненные шаги не повторяются вслепую. Повторный запуск продолжает процесс с последнего подтверждённого шага.

### 5.2. Шаги подключения

1. Оператор GoFuture или уполномоченный менеджер создаёт заявку партнёра.
2. Указываются юридическое наименование, `tenant_id`, разрешённые регионы, юрисдикция данных, ожидаемая нагрузка и нужные интеграции.
3. Сервис управления партнёрами проверяет уникальность `tenant_id` и полноту обязательных параметров.
4. В реестре партнёров создаётся запись со статусом `PROVISIONING`.
5. В Keycloak создаётся отдельный `realm`, базовые роли и приложения-клиенты.
6. При наличии корпоративного поставщика идентификации настраивается федерация OIDC/SAML.
7. Автоматизация инфраструктуры создаёт пространство имён GKE, квоты, сетевые политики и сервисные учётные записи.
8. Создаются отдельные доменные базы PostgreSQL, учётные записи баз и секреты.
9. Создаются Redis/Elasticsearch-области и необходимые региональные Kafka-топики с ACL.
10. В Сервис конфигурации партнёров записывается начальная конфигурация, флаги возможностей и ссылки на секреты внешних интеграций.
11. Для мониторинга автоматически создаются панели, правила оповещений и фильтры по `tenant_id`.
12. Выполняются проверочные запросы: аутентификация, запись/чтение тестовой сущности, публикация события Kafka и получение метрик.
13. Только после успешных проверок партнёр переводится в состояние `ACTIVE`.
14. Владелец партнёра получает приглашение в административный портал.

### 5.3. Идемпотентность подключения

У каждого шага есть устойчивый ключ операции:

`<tenant_id>:<step_name>`.

Сервис управления партнёрами хранит результат шага. Если процесс перезапущен после сбоя, он сначала проверяет уже созданный ресурс и не создаёт второй `realm`, вторую базу или второй набор топиков.

Если шаг невозможно завершить, партнёр не переводится в `ACTIVE`. Частично созданные ресурсы остаются помеченными как принадлежащие этому `tenant_id` и могут быть безопасно продолжены или удалены отдельной процедурой.

## 6. Мониторинг многотенантного окружения

Существующий контур наблюдаемости сохраняется: Prometheus, Grafana, Alertmanager, Loki, OpenTelemetry и Jaeger.

Добавляется контекст партнёра.

### 6.1. Метрики

Для ограниченного набора метрик допускается метка `tenant_id`:

- скорость запросов;
- доля ошибок;
- p95/p99 задержки;
- число активных поездок;
- число сообщений Kafka;
- отставание групп потребителей;
- использование квоты ЦП и памяти;
- число подключений к доменным базам;
- заполнение хранилищ;
- число ошибок SSO;
- число отказов авторизации;
- длительность процесса подключения партнёра;
- количество неуспешных шагов подключения.

В метки не помещаются `user_id`, `booking_id`, `driver_id` и другие высококардинальные идентификаторы.

### 6.2. Журналы

В журналы добавляется `tenant_id` как структурированное поле вместе с `trace_id`, `correlation_id` и `saga_id`.

Для Loki `tenant_id` не обязан быть индексной меткой во всех потоках. Если число партнёров вырастет настолько, что метка станет дорогой по кардинальности, она остаётся полем записи и используется при запросе через структурированный журнал.

### 6.3. Распределённые трассы

OpenTelemetry добавляет атрибут `tenant.id` к трассе после доверенного определения партнёра на шлюзе. Это позволяет проследить запрос одного партнёра через Booking, Pricing, Payments, Fraud и Kafka без раскрытия данных другого партнёра.

### 6.4. Панели Grafana

Предусматриваются два уровня панелей:

- **платформенные** — все партнёры, регионы, общая ёмкость и системные ошибки;
- **партнёрские** — только один `tenant_id`: доступность, задержки, ошибки, квоты, Kafka, состояние доменных баз и SSO.

Доступ к партнёрским панелям также проходит через Keycloak. Пользователь партнёра видит только свою папку Grafana.

### 6.5. Основные оповещения

| Сигнал | Условие |
|---|---|
| Ошибки API партнёра | рост доли 5xx для одного `tenant_id` |
| Рост задержки | p95/p99 выше установленного порога партнёра |
| Исчерпание квоты | использование ЦП, памяти или соединений приближается к лимиту |
| Kafka отстаёт | растёт отставание группы потребителей партнёра |
| База недоступна | недоступна одна из доменных баз партнёра |
| Ошибки SSO | растёт число неуспешных входов или ошибок федерации |
| Нарушение изоляции | зафиксирована попытка доступа к ресурсу другого `tenant_id` |
| Подключение зависло | партнёр слишком долго находится в `PROVISIONING` или `VERIFYING` |

Alertmanager маршрутизирует системные оповещения SRE-команде, а партнёрские — команде сопровождения и, при необходимости, ответственному контакту партнёра.

## 7. Согласованность с предыдущей архитектурой

Многотенантность не меняет границы доменов и не вводит общую междоменную базу.

Сохраняются:

- отдельное владение данными Booking, Driver, Geography, Pricing, Payments, Fraud и Notification;
- региональные идентификаторы `sg`, `jkt`, `sao`, `scl`;
- `home_region` и механизм регионального владения;
- Apache Kafka и Flink;
- транзакционный исходящий журнал;
- региональный шлюз программного интерфейса;
- межрегиональное аварийное восстановление.

Добавляется ещё одно измерение маршрутизации:

`регион → партнёр → домен`.

Для новой операции сначала выбирается допустимый регион, затем по токену определяется партнёрская ячейка, после чего запрос передаётся в доменный сервис этого партнёра.

Для событий путь выглядит аналогично:

`региональный Kafka → пространство топиков tenant_id → доменный поток`.

## 8. Альтернативы

### 8.1. Общие таблицы с колонкой tenant_id

**Плюсы:** меньше баз и проще первоначальное развёртывание.

**Минусы:** ошибка фильтра в одном запросе может раскрыть данные другого партнёра; сложнее независимые резервные копии, миграции и удаление данных партнёра.

**Решение:** не использовать для операционных доменных данных.

### 8.2. Полностью отдельный кластер для каждого партнёра

**Плюсы:** максимальная физическая изоляция.

**Минусы:** высокая стоимость и большое количество инфраструктуры даже для небольшого партнёра.

**Решение:** не использовать по умолчанию. Выделенный кластер остаётся вариантом для крупных или регуляторно чувствительных партнёров.

### 8.3. Один общий Keycloak realm

**Плюсы:** проще управление IAM.

**Минусы:** сложнее независимая федерация SSO, выше риск ошибочного назначения межпартнёрской роли, сложнее раздельные политики токенов.

**Решение:** отдельный `realm` на партнёра.

### 8.4. Отдельная ветка приложения на каждого партнёра

**Плюсы:** можно быстро внести любое уникальное изменение.

**Минусы:** версии быстро расходятся, обновления безопасности и исправления приходится переносить во множество веток.

**Решение:** отклонено. Используются конфигурация, флаги возможностей и адаптеры интеграций.

## 9. Компромиссы и риски

1. **Количество баз данных растёт вместе с числом партнёров.**  
   *Меры:* автоматизированное создание, единый каталог подключений, шаблонные миграции и отдельные выделенные экземпляры только там, где они действительно нужны.

2. **Отдельный Keycloak realm на партнёра увеличивает административную нагрузку.**  
   *Меры:* realm создаётся только автоматизированным процессом, конфигурация версионируется, стандартные роли одинаковы для всех партнёров.

3. **Метка `tenant_id` может увеличить кардинальность метрик.**  
   *Меры:* использовать её только для ограниченного набора партнёрских метрик и не добавлять высококардинальные бизнес-идентификаторы.

4. **Ошибка в автоматическом подключении может оставить частично созданное окружение.**  
   *Меры:* идемпотентные шаги, явные состояния процесса, маркировка всех ресурсов `tenant_id`, проверка перед переводом в `ACTIVE`.

5. **Слишком свободная кастомизация приведёт к скрытым форкам продукта.**  
   *Меры:* кастомизация только через утверждённые конфигурационные точки и адаптеры; новая бизнес-логика проходит обычный архитектурный процесс.

6. **Сотрудникам GoFuture иногда нужен доступ для поддержки.**  
   *Меры:* постоянного межпартнёрского доступа нет; используется временный аварийный доступ с подтверждением и аудитом.
