# ADR-004: Многотенантная платформа GoFuture для партнёров

**Статус:** На рассмотрении  
**Автор:** Александр Вафин  
**Заинтересованные стороны:** продуктовые команды GoFuture, платформенная команда, SRE-команда, информационная безопасность, команда сопровождения партнёров, архитектурный комитет  
**Дата:** 2026-09-15

---

## 1. Контекст

GoFuture должен быстро подключать партнёров в новых регионах и при этом не допускать смешения их данных. Партнёром может быть локальный сервис такси, банк, маркетплейс или другая компания, которая использует платформу GoFuture под своим брендом и с собственным набором интеграций.

Предыдущие архитектурные решения уже задали основу платформы:

- восемь доменных сервисов: Booking, Driver, Pricing, Payments, Notification, Geography, Analytics и Fraud;
- отдельное владение данными каждого домена;
- событийный обмен через Apache Kafka;
- потоковую обработку Apache Flink;
- глобальное развёртывание в нескольких регионах;
- региональный шлюз программного интерфейса;
- единый контур наблюдаемости на Prometheus, Grafana, Loki, OpenTelemetry и Jaeger.

Многотенантность должна дополнять эту архитектуру, а не создавать отдельную ветку кода для каждого партнёра. Основные задачи — ввести устойчивый контекст партнёра, изолировать его вычислительные и информационные ресурсы, автоматизировать создание окружения, поддержать единый вход и ролевой доступ, а также обеспечить мониторинг каждого партнёрского контура.

## 2. Требования

### 2.1. Функциональные требования

| № | Требование |
|---|---|
| **ФТ-01** | Для каждого партнёра должен существовать уникальный `tenant_id`, используемый во всех сервисах, событиях и служебных процессах. |
| **ФТ-02** | Данные одного партнёра не должны быть доступны пользователям, сервисным учётным записям и процессам другого партнёра. |
| **ФТ-03** | Пользователи партнёра должны входить через единый вход с поддержкой OIDC или SAML. |
| **ФТ-04** | Права пользователей должны определяться ролями и областями доступа конкретного партнёра. |
| **ФТ-05** | Подключение нового партнёра должно выполняться автоматически без ручного создания баз, секретов, ролей, топиков и панелей мониторинга. |
| **ФТ-06** | Партнёр должен иметь собственную конфигурацию функций, интеграций, ограничений, оформления и квот. |
| **ФТ-07** | События Kafka должны сохранять принадлежность конкретному партнёру и не смешиваться с событиями других партнёров. |
| **ФТ-08** | Мониторинг должен позволять видеть состояние платформы как в целом, так и по конкретному `tenant_id`. |
| **ФТ-09** | GoFuture должен иметь контролируемый аварийный доступ к окружению партнёра только по отдельной процедуре с аудитом. |
| **ФТ-10** | Партнёр должен иметь возможность использовать собственного корпоративного поставщика идентификации без изменения прикладных сервисов GoFuture. |
| **ФТ-11** | Партнёр должен иметь возможность независимо резервировать, восстанавливать и удалять свои данные без воздействия на данные других партнёров. |

### 2.2. Нефункциональные требования

| № | Категория | Требование | Критичность |
|---|---|---|---|
| **НФТ-01** | Изоляция | В рабочих таблицах не должно быть смешения строк разных партнёров. Для каждого партнёра создаются отдельные логические базы данных каждого домена. | Критичная |
| **НФТ-02** | Безопасность | `tenant_id` нельзя принимать как доверенное значение из заголовка, строки запроса или тела клиентского запроса. Контекст партнёра определяется из проверенного токена. | Критичная |
| **НФТ-03** | Масштабирование | Нагрузка одного партнёра не должна блокировать остальных; применяются независимые квоты и ограничения ресурсов. | Критичная |
| **НФТ-04** | Поддерживаемость | Кастомизация выполняется настройками, флагами возможностей и адаптерами интеграций без отдельной ветки исходного кода партнёра. | Высокая |
| **НФТ-05** | Наблюдаемость | Метрики, журналы и трассы должны содержать контекст партнёра без неконтролируемого роста кардинальности метрик. | Высокая |
| **НФТ-06** | Аудит | Изменение ролей, конфигурации, секретов и аварийный доступ фиксируются в защищённом журнале аудита. | Критичная |
| **НФТ-07** | Региональность | При подключении партнёра указываются разрешённые регионы и юрисдикция данных; процесс создания окружения не должен нарушать правила размещения данных из предыдущего архитектурного решения. | Критичная |
| **НФТ-08** | Автоматизация | Повторный запуск шага подключения должен быть идемпотентным и не создавать дубликаты окружений, ролей, баз и топиков. | Высокая |

## 3. Решение

### 3.1. Общая модель

Выбирается модель **общего управляющего контура и изолированных партнёрских ячеек**.

Управляющий контур отвечает за:

- реестр партнёров;
- управление идентификацией и доступом;
- конфигурацию партнёров;
- автоматическое создание окружений;
- общую наблюдаемость;
- аудит административных действий.

Для каждого партнёра создаётся отдельная логическая ячейка внутри разрешённого регионального контура. По умолчанию это отдельное пространство имён в региональном GKE со своими сервисными учётными записями, сетевыми политиками, квотами, секретами, хранилищами и **отдельными развёртываниями необходимых доменных сервисов**.

Образы приложений и версии сервисов остаются общими для всех партнёров. Изоляция достигается отдельными развёртываниями и конфигурацией, а не отдельными ветками исходного кода.

Если нормативные требования или нагрузка конкретного партнёра требуют физического разделения, тот же шаблон разворачивается в выделенном кластере без изменения прикладной модели.

Диаграмма верхнего уровня: [`C2-multitenant-platform.puml`](./C2-multitenant-platform.puml).

### 3.2. Идентификатор партнёра

Каждому партнёру присваивается неизменяемый `tenant_id`, например `bank-a` или `taxi-partner-17`.

`tenant_id` используется:

- в реестре партнёров;
- в токене пользователя и сервисной учётной записи;
- в конфигурации шлюза программного интерфейса;
- в именах партнёрских Kafka-топиков и групп потребителей;
- в атрибутах трассировки;
- в ограниченном наборе метрик;
- в журналах аудита;
- в привязке к доменным и аналитическим хранилищам.

Клиент не может самостоятельно выбрать `tenant_id`. Шлюз проверяет подпись и издателя токена, извлекает принадлежность к партнёру из доверенных утверждений токена и передаёт этот контекст дальше. При несовпадении партнёра в маршруте, токене и реестре запрос отклоняется.

### 3.3. Изоляция вычислительного контура

Для каждого партнёра создаётся отдельное пространство имён Kubernetes:

`tenant-<tenant_id>`.

В нём создаются:

- отдельные развёртывания необходимых доменных сервисов;
- отдельные сервисные учётные записи;
- `ResourceQuota` и `LimitRange`;
- сетевые политики с запретом по умолчанию;
- ссылки только на секреты этого партнёра;
- конфигурация включённых возможностей;
- разрешённые интеграции.

Такой подход позволяет масштабировать партнёров независимо и не допускает, чтобы один партнёр исчерпал ресурсы остальных.

### 3.4. Изоляция операционных данных

Для выполнения требования полной изоляции не используется одна общая таблица с колонкой `tenant_id`.

Для каждого партнёра создаются отдельные логические базы PostgreSQL по доменам:

- `<tenant_id>_booking`;
- `<tenant_id>_driver`;
- `<tenant_id>_geography`;
- `<tenant_id>_pricing`;
- `<tenant_id>_payments`;
- `<tenant_id>_fraud`;
- `<tenant_id>_notification`.

Физически несколько таких баз могут размещаться на одном управляемом кластере PostgreSQL, если это допускается требованиями партнёра. Изоляция обеспечивается отдельными базами, отдельными пользователями базы и отдельными секретами.

Сохраняется правило доменного владения из предыдущих заданий: Booking работает только со своей базой, Payments — только со своей, Geography — только со своей и так далее. То, что на C2 сервисы и базы внутри ячейки показаны укрупнённо, не означает общего междоменного доступа.

Для оперативных хранилищ используется тот же принцип:

- отдельная логическая область Redis Driver;
- отдельная логическая область Redis Pricing;
- отдельная логическая область Redis Geography;
- отдельный индекс Elasticsearch Geography;
- отдельные учётные данные и права доступа.

Для партнёров с повышенными требованиями эти хранилища могут быть выделены физически.

### 3.5. Изоляция аналитических данных

Analytics не получает права прямого чтения рабочих таблиц других доменов. Он получает данные через согласованные события и формирует аналитические представления в ClickHouse.

Для каждого партнёра создаётся отдельная логическая база ClickHouse и отдельные права доступа. Аналитик партнёра получает доступ только к подготовленным агрегированным или обезличенным представлениям своего `tenant_id`.

### 3.6. Резервное копирование, восстановление и удаление данных партнёра

Отдельные базы и пространства хранения позволяют независимо управлять жизненным циклом данных каждого партнёра.

Для каждого `tenant_id` предусматриваются:

- независимый набор резервных копий доменных баз;
- независимое восстановление в отдельное временное окружение для проверки;
- отдельные сроки хранения резервных копий в соответствии с договором и юрисдикцией;
- управляемое удаление данных при завершении договора;
- отдельная процедура удаления секретов, Kafka-топиков, аналитических данных и поисковых индексов.

Удаление партнёра выполняется только после подтверждения, завершения срока хранения и формирования записи в журнале аудита. Данные других партнёров при этом не затрагиваются.

### 3.7. Изоляция событий Kafka

Региональное разделение из событийной архитектуры сохраняется. Для партнёрских событий имя топика расширяется идентификатором партнёра:

`gofuture.<region>.<tenant_id>.<domain>.<stream>.v1`.

Внутренний код региона берётся из ранее принятой схемы:

- `sg` — Сингапур;
- `jkt` — Джакарта;
- `sao` — Сан-Паулу;
- `scl` — Сантьяго.

Примеры:

- `gofuture.sg.bank-a.booking.events.v1`;
- `gofuture.sg.bank-a.payments.events.v1`;
- `gofuture.jkt.taxi-partner-17.driver.location.v1`.

Для каждого партнёра автоматически создаются:

- необходимые топики;
- группы потребителей;
- Kafka ACL;
- топики повторной обработки;
- топики недоставленных сообщений.

Сервисная учётная запись партнёра получает права только на его пространство топиков.

### 3.8. Конфигурация и кастомизация

Создаётся **Сервис конфигурации партнёров**. Он хранит:

- включённые возможности;
- ограничения по продуктам;
- правила брендирования;
- разрешённые платёжные и картографические поставщики;
- ссылки на секреты интеграций;
- региональные параметры;
- квоты;
- версии конфигурации.

Владелец партнёра изменяет только разрешённую часть конфигурации через портал. Поток выглядит так:

`Портал партнёра → шлюз программного интерфейса → Сервис конфигурации партнёров`.

Перед изменением шлюз и сервис проверяют `tenant_id`, роль пользователя и перечень разрешённых параметров. Все изменения записываются в журнал аудита.

Создание отдельной ветки исходного кода под конкретного партнёра считается нежелательным решением. Отличия реализуются конфигурацией, флагами возможностей и адаптерами интеграций.

## 4. Управление идентификацией и доступом

### 4.1. Выбор IAM

Для административного и партнёрского доступа выбирается **Keycloak**.

Причины выбора:

- поддержка OpenID Connect и SAML;
- федерация с внешними поставщиками идентификации;
- ролевой доступ;
- отдельные области безопасности для партнёров;
- возможность развёртывания в собственной инфраструктуре;
- отсутствие зависимости прикладных сервисов от корпоративного каталога конкретного партнёра.

Для каждого партнёра создаётся отдельная область безопасности Keycloak (`realm`). Она содержит собственных пользователей, группы, роли, приложения-клиенты и настройки федерации.

Управляющие пользователи GoFuture находятся в отдельной служебной области безопасности и не получают автоматического доступа к данным партнёров.

### 4.2. Единый вход

Если у партнёра есть собственный поставщик идентификации, его область безопасности Keycloak связывается с ним по OIDC или SAML.

Путь входа:

1. пользователь открывает портал партнёра;
2. определяется область безопасности соответствующего партнёра;
3. при настроенной федерации пользователь перенаправляется к корпоративному поставщику идентификации;
4. после успешной аутентификации Keycloak выпускает токен GoFuture;
5. токен содержит `tenant_id`, роли и области доступа;
6. шлюз программного интерфейса проверяет токен и формирует внутренний контекст партнёра.

### 4.3. Управление пользователями и ролями

Владелец партнёра управляет пользователями и ролями через портал. Поток управления идёт через шлюз программного интерфейса в Keycloak и ограничивается текущим `tenant_id`.

Пользователь одного партнёра не может получить роль другого партнёра. Права проверяются на двух уровнях:

1. шлюз отсекает запросы без требуемой области доступа;
2. доменный сервис проверяет право на конкретную бизнес-операцию.

Подробная матрица приведена в [`roles-access.md`](./roles-access.md).

### 4.4. Аварийный доступ GoFuture

Для поддержки критического инцидента предусматривается отдельная процедура временного доступа:

- постоянного межпартнёрского доступа у сотрудников GoFuture нет;
- доступ выдаётся на ограниченное время;
- требуется подтверждение ответственного лица;
- назначается конкретный партнёр и причина;
- все действия записываются в журнал аудита;
- после истечения времени роль отзывается автоматически.

## 5. Автоматическое подключение нового партнёра

Подробный поток показан на [`C3-partner-provisioning.puml`](./C3-partner-provisioning.puml).

Создаётся **Сервис управления партнёрами**, который хранит состояние подключения и запускает идемпотентный процесс подготовки окружения.

### 5.1. Состояния подключения

Партнёр проходит состояния:

`DRAFT → VALIDATING → PROVISIONING → VERIFYING → ACTIVE`.

При ошибке процесс переходит в `FAILED`. Повторный запуск продолжает процесс с последнего подтверждённого шага.

### 5.2. Региональное размещение

В заявке указываются разрешённые регионы и юрисдикция данных. Сервис управления партнёрами выбирает только регион, разрешённый политикой размещения данных.

Используются внутренние коды `sg`, `jkt`, `sao`, `scl`. Автоматизация создаёт партнёрскую ячейку именно в соответствующем региональном GKE-кластере, а Kafka-топики создаются в Kafka выбранного региона.

Это продолжает модель глобального развёртывания из предыдущего архитектурного решения и не вводит отдельную региональную схему для партнёров.

### 5.3. Шаги подключения

1. Оператор GoFuture или уполномоченный менеджер создаёт заявку партнёра.
2. Указываются юридическое наименование, `tenant_id`, разрешённые регионы, юрисдикция данных, ожидаемая нагрузка и нужные интеграции.
3. Проверяются уникальность `tenant_id`, полнота данных и допустимость региона.
4. В реестре создаётся запись со статусом `PROVISIONING` и внутренним кодом региона.
5. В Keycloak создаётся отдельная область безопасности, базовые роли и приложения-клиенты.
6. При наличии корпоративного поставщика идентификации настраивается федерация OIDC/SAML.
7. В выбранном региональном GKE создаются пространство имён, отдельные развёртывания сервисов, квоты, сетевые политики и сервисные учётные записи.
8. Создаются отдельные доменные базы PostgreSQL, Redis/Elasticsearch-области и аналитическая база ClickHouse.
9. В Kafka выбранного региона создаются партнёрские топики, группы потребителей и ACL.
10. Создаются начальная конфигурация, флаги возможностей и ссылки на секреты внешних интеграций.
11. Для наблюдаемости создаются правила оповещений, панели и фильтры по `tenant_id`.
12. Выполняются проверочные запросы: федеративный вход при его наличии, аутентификация, запись только в хранилища партнёра, публикация события Kafka и получение метрик, журналов и трасс.
13. Только после успешных проверок партнёр переводится в состояние `ACTIVE`.
14. Владелец партнёра получает приглашение в административный портал.

### 5.4. Идемпотентность подключения

У каждого шага есть устойчивый ключ операции:

`<tenant_id>:<step_name>`.

Сервис управления партнёрами хранит результат шага. Если процесс перезапущен после сбоя, он сначала проверяет уже созданный ресурс и не создаёт вторую область безопасности, вторую базу, второе развёртывание или второй набор топиков.

Если шаг невозможно завершить, партнёр не переводится в `ACTIVE`. Частично созданные ресурсы остаются помеченными `tenant_id` и могут быть безопасно продолжены или удалены отдельной процедурой.

## 6. Мониторинг многотенантного окружения

Существующий контур наблюдаемости сохраняется: Prometheus, Grafana, Alertmanager, Loki, OpenTelemetry и Jaeger.

Grafana рассматривается как **внутренний инструмент GoFuture** для SRE и платформенной команды. Партнёры не получают прямого доступа к общей Grafana и общему источнику Prometheus. Если партнёру нужно показать эксплуатационные показатели, они выводятся в его портал через отдельный прикладной интерфейс с обязательной фильтрацией по `tenant_id`.

### 6.1. Что контролируется

Prometheus получает данные не только от прикладных сервисов, но и от инфраструктурных экспортёров:

- Kafka Exporter — состояние партнёрских топиков и отставание групп потребителей;
- PostgreSQL Exporter — состояние доменных баз и число соединений;
- kube-state-metrics — квоты, развёртывания и состояния партнёрских пространств имён;
- метрики Keycloak — состояние IAM и ошибки SSO;
- метрики Сервиса управления партнёрами — длительность и ошибки подключения.

### 6.2. Метрики

Для ограниченного набора метрик допускается метка `tenant_id`:

- скорость запросов;
- доля ошибок;
- p95/p99 задержки;
- число активных поездок;
- число сообщений Kafka;
- отставание групп потребителей;
- использование квоты ЦП и памяти;
- число подключений к доменным базам;
- заполнение хранилищ;
- число ошибок SSO;
- число отказов авторизации;
- длительность процесса подключения партнёра;
- количество неуспешных шагов подключения.

В метки не помещаются `user_id`, `booking_id`, `driver_id` и другие высококардинальные идентификаторы.

### 6.3. Журналы

В журналы добавляется `tenant_id` как структурированное поле вместе с `trace_id`, `correlation_id` и `saga_id`.

Доменные сервисы, Keycloak и Сервис управления партнёрами отправляют журналы в Loki. `tenant_id` не обязан быть индексной меткой во всех потоках: при росте числа партнёров он может храниться как структурированное поле записи.

### 6.4. Распределённые трассы

OpenTelemetry передаёт атрибут `tenant.id` после доверенного определения партнёра на шлюзе. Это позволяет проследить запрос конкретного партнёра через Booking, Pricing, Payments, Fraud и Kafka без смешения с трассами другого партнёра.

### 6.5. Основные оповещения

| Сигнал | Условие |
|---|---|
| Ошибки API партнёра | рост доли 5xx для одного `tenant_id` |
| Рост задержки | p95/p99 выше установленного порога |
| Исчерпание квоты | использование ЦП, памяти или соединений приближается к лимиту |
| Kafka отстаёт | растёт отставание группы потребителей партнёра |
| База недоступна | недоступна одна из доменных баз партнёра |
| Ошибки SSO | растёт число неуспешных входов или ошибок федерации |
| Нарушение изоляции | зафиксирована попытка доступа к ресурсу другого `tenant_id` |
| Подключение зависло | партнёр слишком долго находится в `PROVISIONING` или `VERIFYING` |

Alertmanager маршрутизирует системные оповещения SRE-команде, а партнёрские — команде сопровождения и ответственному контакту партнёра.

## 7. Согласованность с предыдущей архитектурой

Многотенантность не меняет границы доменов и не вводит общую междоменную базу.

Сохраняются:

- отдельное владение данными Booking, Driver, Geography, Pricing, Payments, Fraud и Notification;
- региональные идентификаторы `sg`, `jkt`, `sao`, `scl`;
- `home_region` и механизм регионального владения;
- Apache Kafka и Flink;
- транзакционный исходящий журнал;
- региональный шлюз программного интерфейса;
- межрегиональное аварийное восстановление.

Добавляется ещё одно измерение маршрутизации:

`регион → партнёр → домен`.

Для новой операции сначала выбирается допустимый регион, затем по токену определяется партнёрская ячейка, после чего запрос передаётся в доменный сервис этого партнёра.

Для событий путь выглядит аналогично:

`региональный Kafka → пространство топиков tenant_id → доменный поток`.

## 8. Альтернативы

### 8.1. Общие таблицы с колонкой tenant_id

**Плюсы:** меньше баз и проще первоначальное развёртывание.

**Минусы:** ошибка фильтра в одном запросе может раскрыть данные другого партнёра; сложнее независимые резервные копии, восстановление и удаление данных партнёра.

**Решение:** не использовать для операционных доменных данных.

### 8.2. Полностью отдельный кластер для каждого партнёра

**Плюсы:** максимальная физическая изоляция.

**Минусы:** высокая стоимость и большое количество инфраструктуры даже для небольшого партнёра.

**Решение:** не использовать по умолчанию. Выделенный кластер остаётся вариантом для крупных или регуляторно чувствительных партнёров.

### 8.3. Одна общая область безопасности Keycloak

**Плюсы:** проще управление IAM.

**Минусы:** сложнее независимая федерация SSO, выше риск ошибочного назначения межпартнёрской роли, сложнее отдельные политики токенов.

**Решение:** отдельная область безопасности на партнёра.

### 8.4. Отдельная ветка приложения на каждого партнёра

**Плюсы:** можно быстро внести уникальное изменение.

**Минусы:** версии расходятся, обновления безопасности и исправления приходится переносить во множество веток.

**Решение:** отклонено. Используются конфигурация, флаги возможностей и адаптеры интеграций.

## 9. Компромиссы и риски

1. **Количество баз данных растёт вместе с числом партнёров.**  
   *Меры:* автоматизированное создание, единый каталог подключений, шаблонные миграции и выделенные экземпляры только там, где они действительно нужны.

2. **Отдельная область безопасности Keycloak на партнёра увеличивает административную нагрузку.**  
   *Меры:* создание только автоматизированным процессом, версионируемая конфигурация, единый набор базовых ролей.

3. **Метка `tenant_id` может увеличить кардинальность метрик.**  
   *Меры:* использовать её только для ограниченного набора партнёрских метрик и не добавлять высококардинальные бизнес-идентификаторы.

4. **Ошибка автоматического подключения может оставить частично созданное окружение.**  
   *Меры:* идемпотентные шаги, явные состояния процесса, маркировка всех ресурсов `tenant_id`, проверка перед переводом в `ACTIVE`.

5. **Слишком свободная кастомизация приведёт к скрытым ответвлениям продукта.**  
   *Меры:* кастомизация только через утверждённые конфигурационные точки и адаптеры; новая бизнес-логика проходит обычный архитектурный процесс.

6. **Сотрудникам GoFuture иногда нужен доступ для поддержки.**  
   *Меры:* постоянного межпартнёрского доступа нет; используется временный аварийный доступ с подтверждением и аудитом.

7. **Отдельные развёртывания сервисов увеличивают расход ресурсов.**  
   *Меры:* минимальные базовые лимиты, горизонтальное масштабирование по фактической нагрузке и объединение только тех инфраструктурных компонентов, где изоляция обеспечивается независимо от приложения.
