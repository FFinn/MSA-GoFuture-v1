# Задание 4. Проектируем систему мониторинга

В рамках задания спроектирована многотенантная платформа GoFuture для быстрого подключения партнёров с изоляцией данных, ролевым доступом, единым входом, автоматическим созданием окружения и отдельным мониторингом каждого партнёра.

## Артефакты

- [`ADR-004-multitenant-platform.md`](./ADR-004-multitenant-platform.md) — модель изоляции партнёров, IAM и SSO, автоматическое подключение, конфигурация функций, мониторинг, альтернативы и риски.
- [`C2-multitenant-platform.puml`](./C2-multitenant-platform.puml) — C2-диаграмма управляющего контура, Keycloak, партнёрских ячеек, изолированных хранилищ, событий и наблюдаемости.
- [`C3-partner-provisioning.puml`](./C3-partner-provisioning.puml) — C3-диаграмма автоматического процесса подключения нового партнёра.
- [`roles-access.md`](./roles-access.md) — таблица ролей и уровней доступа к данным.

## Основные решения

Платформа строится по модели **общего управляющего контура и изолированных партнёрских ячеек**. Каждый партнёр получает неизменяемый `tenant_id`, отдельное пространство имён Kubernetes, сервисные учётные записи, сетевые политики, квоты, секреты и отдельные логические базы PostgreSQL каждого домена.

Для операционных данных не используется одна общая таблица с колонкой `tenant_id`: базы партнёров разделены. Это снижает риск утечки из-за ошибки фильтра и позволяет независимо выполнять резервное копирование, миграцию и удаление данных партнёра.

В Apache Kafka для партнёрских событий используется пространство имён:

`gofuture.<region>.<tenant_id>.<domain>.<stream>.v1`.

IAM реализуется на Keycloak. Для каждого партнёра создаётся отдельный `realm`, а корпоративный единый вход подключается по OIDC или SAML. `tenant_id` определяется только из проверенного токена и не доверяется значению, которое клиент передал самостоятельно.

Подключение нового партнёра автоматизировано через Сервис управления партнёрами. Он последовательно создаёт запись в реестре, `realm` и роли Keycloak, инфраструктуру Kubernetes, доменные хранилища, Kafka-топики и ACL, конфигурацию, секреты, панели мониторинга и правила оповещений. Перед переводом партнёра в `ACTIVE` выполняются проверочные запросы.

Кастомизация выполняется конфигурацией, флагами возможностей и адаптерами интеграций. Отдельная ветка исходного кода для каждого партнёра не создаётся.

Существующий контур наблюдаемости Prometheus, Grafana, Alertmanager, Loki, OpenTelemetry и Jaeger сохраняется. Для ограниченного набора метрик добавляется `tenant_id`; в журналах и трассах он используется как структурированный контекст. Высококардинальные идентификаторы пользователей, поездок и водителей в метки Prometheus не добавляются.
