# Задание 4. Проектируем систему мониторинга

В рамках задания спроектирована многотенантная платформа GoFuture для быстрого подключения партнёров с полной изоляцией данных, ролевым доступом, единым входом, автоматическим созданием окружения и мониторингом каждого партнёрского контура.

## Артефакты

- [`ADR-004-multitenant-platform.md`](./ADR-004-multitenant-platform.md) — модель изоляции партнёров, IAM и SSO, автоматическое подключение, конфигурация функций, наблюдаемость, альтернативы и риски.
- [`C2-multitenant-platform.puml`](./C2-multitenant-platform.puml) — C2-диаграмма управляющего контура, Keycloak, партнёрских ячеек, изолированных хранилищ, событий и мониторинга.
- [`C3-partner-provisioning.puml`](./C3-partner-provisioning.puml) — C3-диаграмма автоматического процесса подключения нового партнёра.
- [`roles-access.md`](./roles-access.md) — таблица ролей и уровней доступа к данным.

## Основные решения

Платформа строится по модели **общего управляющего контура и изолированных партнёрских ячеек**. Каждый партнёр получает неизменяемый `tenant_id`, отдельное пространство имён Kubernetes, отдельные развёртывания необходимых доменных сервисов из общих версий образов, сервисные учётные записи, сетевые политики, квоты, секреты и отдельные логические хранилища.

Для операционных данных не используется одна общая таблица с колонкой `tenant_id`: для каждого партнёра создаются отдельные базы PostgreSQL каждого домена. Доменное владение сохраняется — Booking работает только со своей базой, Payments только со своей и так далее. Analytics получает данные через события и использует отдельную логическую базу ClickHouse партнёра. Redis и Elasticsearch также разделяются логически и защищаются отдельными учётными данными.

Такая модель позволяет независимо создавать резервные копии, восстанавливать и удалять данные одного партнёра, не затрагивая остальных.

В Apache Kafka для партнёрских событий используется пространство имён:

`gofuture.<region>.<tenant_id>.<domain>.<stream>.v1`.

Внутренние коды регионов сохраняются из предыдущего архитектурного решения: `sg`, `jkt`, `sao`, `scl`.

IAM реализуется на Keycloak. Для каждого партнёра создаётся отдельная область безопасности Keycloak (`realm`), а корпоративный единый вход подключается по OIDC или SAML. `tenant_id` определяется только из проверенного токена и не доверяется значению, которое клиент передал самостоятельно.

Владелец партнёра управляет пользователями, ролями и разрешённой бизнес-конфигурацией через портал. Все административные операции проходят через шлюз программного интерфейса, ограничиваются текущим `tenant_id` и записываются в журнал аудита.

Подключение нового партнёра автоматизировано через Сервис управления партнёрами. Он последовательно создаёт запись в реестре, область безопасности и роли Keycloak, федерацию SSO при её наличии, отдельные развёртывания сервисов в разрешённом региональном GKE, доменные и аналитические хранилища, Kafka-топики и ACL, конфигурацию, секреты и правила мониторинга. Перед переводом партнёра в `ACTIVE` выполняются проверки SSO, изоляции данных, Kafka и телеметрии.

Кастомизация выполняется конфигурацией, флагами возможностей и адаптерами интеграций. Отдельная ветка исходного кода для каждого партнёра не создаётся.

Мониторинг построен на существующем контуре Prometheus, Grafana, Alertmanager, Loki, OpenTelemetry и Jaeger. Prometheus дополнительно получает метрики Kafka, доменных баз, Kubernetes и Keycloak через соответствующие экспортёры. `tenant_id` используется только для ограниченного набора метрик; высококардинальные идентификаторы пользователей, поездок и водителей в метки Prometheus не добавляются.

Grafana остаётся внутренним инструментом GoFuture для SRE и платформенной команды. Партнёры не получают прямого доступа к общему источнику Prometheus; при необходимости эксплуатационные показатели выводятся в портал через отдельный прикладной интерфейс с обязательной фильтрацией по `tenant_id`.
