# ADR-003: Глобальное развёртывание GoFuture

**Статус:** На рассмотрении  
**Автор:** Александр Вафин  
**Заинтересованные стороны:** продуктовые команды GoFuture, платформенная команда, SRE-команда, инженеры данных, архитектурный комитет, информационная безопасность  
**Дата:** 2026-09-15

---

## 1. Контекст

GoFuture должен обеспечить доступность критических сервисов не ниже **99,99%** и низкую задержку для пользователей в Юго-Восточной Азии и Южной Америке. Для этого требуется работа более чем в трёх географических регионах, локальная обработка трафика, региональная отказоустойчивость, репликация критичных данных и формализованное аварийное переключение.

Ранее были определены восемь доменных сервисов и правило отдельного владения данными: Booking, Driver, Pricing, Payments, Notification, Geography, Analytics и Fraud. Событийная платформа добавила Apache Kafka, Apache Flink, Kafka Connect + Debezium, реестр схем, транзакционный исходящий журнал, оркестрационную Saga и единый контур наблюдаемости. Глобальное развёртывание дополняет эти решения, а не заменяет их.

Шлюз программного интерфейса сохраняется и разворачивается в каждом регионе. Общий путь нового запроса выглядит так:

`клиент → глобальный балансировщик → региональный шлюз программного интерфейса → доменный сервис`.

Для уже существующей сущности одного выбора ближайшего региона недостаточно: запрос должен попадать к текущему владельцу её сегмента данных. Поэтому маршрутизация разделяется на выбор ближайшей площадки для новой операции и маршрутизацию существующей поездки по её региону-владельцу.

В исходном описании компании одновременно указаны Yandex Cloud и названия сервисов AWS. Для глобального контура это архитектурно значимая неоднозначность, потому что целевые пользователи находятся в Юго-Восточной Азии и Южной Америке. В качестве целевой международной платформы выбирается Google Cloud с регионами в обеих требуемых географиях. Существующее развёртывание в Yandex Cloud рассматривается как наследуемый контур на период миграции и не входит в критический путь международной платформы.

## 2. Требования

### 2.1. Функциональные требования

| № | Требование |
|---|---|
| **ФТ-01** | Новая операция должна попадать в ближайший доступный регион без ручного выбора пользователя. |
| **ФТ-02** | Запрос существующей поездки или финансовой операции должен выполняться в регионе, который в данный момент владеет соответствующим сегментом данных. |
| **ФТ-03** | При недоступности региона его сегменты должны переводиться в парный регион по формализованной процедуре аварийного переключения. |
| **ФТ-04** | Критичные данные каждого домена должны иметь резервную копию в другом регионе, пригодную для продолжения работы после аварии. |
| **ФТ-05** | Событийная платформа должна продолжать обработку критичных доменных событий после регионального отказа. |
| **ФТ-06** | Активная поездка и финансовая операция не должны одновременно изменяться двумя регионами как двумя независимыми владельцами записи. |
| **ФТ-07** | Внешний трафик должен проходить через средства защиты до попадания в региональные сервисы. |
| **ФТ-08** | Для каждого региона должны собираться метрики доступности, задержки, состояния аварийного контура и отставания репликации. |

### 2.2. Нефункциональные требования из задания

| № | Категория | Требование | Критичность |
|---|---|---|---|
| **НФТ-01** | Доступность | Доступность критических пользовательских сервисов должна быть не ниже **99,99%**. | Критичная |
| **НФТ-02** | География | Рабочий контур должен быть развёрнут **более чем в трёх географических регионах**. | Критичная |
| **НФТ-03** | Задержка | Новые пользовательские операции должны обслуживаться ближайшим подходящим регионом, чтобы снизить сетевую задержку. | Критичная |
| **НФТ-04** | Отказоустойчивость | Архитектура должна переживать отказ зоны и иметь механизм продолжения работы при отказе целого региона. | Критичная |
| **НФТ-05** | Безопасность | Публичный контур должен быть защищён WAF, сетевым межсетевым экраном и дополнительными сетевыми ограничениями. | Критичная |
| **НФТ-06** | Регуляторные требования | Архитектура должна позволять ограничить хранение и передачу данных допустимой юрисдикцией. | Высокая |

### 2.3. Архитектурные целевые показатели решения

Следующие значения не заданы заказчиком. Это эксплуатационные цели проектируемого решения; их необходимо подтвердить нагрузочными испытаниями и учениями по аварийному восстановлению.

| № | Показатель | Целевое значение |
|---|---|---|
| **АЦ-01** | Время восстановления критического контура при отказе региона | не более 10 минут |
| **АЦ-02** | Отставание межрегиональной реплики критичной базы PostgreSQL в штатном режиме | желательно не более 60 секунд |
| **АЦ-03** | Потеря данных при катастрофическом отказе региона | не больше фактического отставания асинхронной реплики |

## 3. Согласованность с предыдущими решениями

Глобальное развёртывание сохраняет следующие правила:

1. Каждый доменный сервис владеет своей базой PostgreSQL.
2. Прямой доступ к базе другого домена запрещён.
3. Оперативные хранилища Redis логически разделены между Driver, Pricing и Geography.
4. Elasticsearch является геопоисковым индексом Geography, а не общей междоменной базой.
5. Apache Kafka остаётся основным журналом междоменных событий.
6. Kafka Connect + Debezium публикует события из транзакционных исходящих журналов.
7. Apache Flink выполняет потоковые вычисления.
8. Шлюз программного интерфейса остаётся точкой входа в доменные программные интерфейсы.
9. Prometheus, Grafana, Alertmanager, Loki, OpenTelemetry, Jaeger и экспортёры сохраняются как контур наблюдаемости.

На C2 базовые компоненты показаны без красного выделения, а новые инфраструктурные элементы глобального контура отмечены красным.

## 4. Выбор регионов

Для целевого контура выбираются четыре региона Google Cloud:

| География | Регион | Внутренний идентификатор GoFuture | Код Google Cloud | Роль |
|---|---|---|---|---|
| Юго-Восточная Азия | **Сингапур** | `sg` | `asia-southeast1` | Активный регион, парный резерв для Джакарты |
| Юго-Восточная Азия | **Джакарта** | `jkt` | `asia-southeast2` | Активный регион, парный резерв для Сингапура |
| Южная Америка | **Сан-Паулу** | `sao` | `southamerica-east1` | Активный регион, парный резерв для Сантьяго |
| Южная Америка | **Сантьяго** | `scl` | `southamerica-west1` | Активный регион, парный резерв для Сан-Паулу |

### 4.1. Внутренние идентификаторы регионов

Коды `sg`, `jkt`, `sao`, `scl` принадлежат модели GoFuture и не зависят от конкретного поставщика облачной инфраструктуры. Поэтому события и топики Kafka не связываются с кодами Google Cloud.

Примеры:

- `gofuture.sg.booking.events.v1`;
- `gofuture.jkt.booking.events.v1`;
- `gofuture.sao.booking.events.v1`;
- `gofuture.scl.booking.events.v1`.

Если физический регион или поставщик облачной инфраструктуры изменится, контракт событийной платформы останется прежним.

### 4.2. Обоснование выбора

**Сингапур** используется как один из основных узлов Юго-Восточной Азии и образует пару аварийного восстановления с Джакартой.

**Джакарта** является отдельным активным регионом для Индонезии и соседнего трафика, а не только резервной площадкой.

**Сан-Паулу** обслуживает Бразилию и восточную часть Южной Америки.

**Сантьяго** обслуживает западную часть континента и является парным регионом для Сан-Паулу.

Такой выбор даёт четыре рабочих региона в двух целевых географиях. При отказе одного региона переключение сначала выполняется внутри того же макрорегиона, без межконтинентального перехода.

### 4.3. Почему международный контур не остаётся только в Yandex Cloud

Для выполнения требований нужны физические регионы в Юго-Восточной Азии и Южной Америке. Текущий контур Yandex Cloud может использоваться на этапе миграции, но не решает требование низкой задержки для указанных рынков.

Переход на Google Cloud повышает стоимость миграции и требует новых эксплуатационных компетенций. Этот компромисс принимается ради выполнения требований по географии, задержке и региональной отказоустойчивости.

## 5. Региональная модель развёртывания

В каждом из четырёх регионов разворачивается одинаковый набор критических компонентов:

1. региональный кластер GKE в нескольких зонах;
2. региональный экземпляр шлюза программного интерфейса;
3. Booking, Driver, Geography, Pricing, Payments, Fraud, Notification и Analytics;
4. отдельные доменные базы PostgreSQL;
5. оперативные хранилища Redis доменов Driver, Pricing и Geography;
6. геопоисковый индекс Elasticsearch домена Geography;
7. локальный Apache Kafka;
8. реестр схем;
9. Kafka Connect + Debezium;
10. локальный Apache Flink и хранилище его контрольных точек;
11. средства наблюдаемости;
12. клиент аварийного реестра регионального владения.

Отказ одной зоны закрывается внутри регионального GKE-кластера и региональной схемы высокой доступности баз. Перенос в другой географический регион выполняется только при региональной аварии или длительной недоступности критического пути.

Горизонтальное масштабирование сервисов выполняется независимо по регионам. Для сервисов и потребителей Kafka учитываются не только ЦП и память, но также задержка, длина очереди и отставание потребителей.

## 6. Маршрутизация и владение сегментами

Схема: [`geo-routing.puml`](./geo-routing.puml).

### 6.1. Новая операция

Для создания новой поездки используется следующий путь:

1. клиент обращается к единому имени GoFuture;
2. Cloud DNS возвращает адрес глобального внешнего балансировщика;
3. Cloud Armor применяется как политика защиты входящего трафика;
4. глобальный балансировщик выбирает ближайший здоровый регион с допустимым размещением данных и достаточной ёмкостью;
5. запрос передаётся в региональный шлюз программного интерфейса;
6. созданной сущности присваивается `home_region`, равный выбранному региону;
7. идентификатор сущности содержит устойчивый признак домашнего региона, а само значение `home_region` хранится в доменной базе.

### 6.2. Существующая сущность

Для существующей поездки ближайший регион не выбирается заново. Региональный шлюз определяет домашний сегмент по идентификатору сущности и проверяет **реестр активного владельца сегмента**.

Реестр хранит небольшое количество служебных данных:

- `home_region` — исходный сегмент (`sg`, `jkt`, `sao`, `scl`);
- `active_region` — регион, который сейчас обслуживает сегмент;
- `epoch` — поколение владения;
- состояние сегмента: `ACTIVE`, `FENCING`, `PROMOTING`, `DEGRADED`.

Для реестра выбирается глобально согласованное хранилище Cloud Spanner. В нём нет бизнес-данных поездок или платежей — только служебное состояние регионального владения.

Если запрос попал в регион, который не является `active_region` нужного сегмента, шлюз передаёт его в шлюз текущего владельца по защищённому межрегиональному каналу. После аварийного переключения запись `sg → jkt` позволяет обслуживать сегменты Сингапура в Джакарте без изменения идентификаторов бизнес-сущностей.

### 6.3. Выбор доменной базы после аварии

В обычном режиме сервис региона работает со своей доменной базой. После аварии в одном регионе у сервиса парного региона могут одновременно быть доступны два сегмента одного домена: собственный и повышенный резервный.

Например, Booking в Джакарте получает:

- основную Booking PostgreSQL для `home_region=jkt`;
- повышенную Booking PostgreSQL для `home_region=sg`.

Слой доступа к данным выбирает соединение **по `home_region` запроса**, а не по названию текущего физического региона. Это не нарушает доменную границу: Booking по-прежнему обращается только к базам Booking, Payments — только к базам Payments и т. д.

## 7. Репликация данных

Схема: [`data-replication.puml`](./data-replication.puml).

### 7.1. Один владелец записи

Каждая операционная сущность относится к домашнему сегменту `sg`, `jkt`, `sao` или `scl`. В штатном режиме домашний сегмент обслуживается одноимённым регионом.

Право записи определяется не только `home_region`, но и текущим `epoch` в реестре владения. Сервис может выполнять запись только при наличии действующей короткоживущей аренды для текущего поколения сегмента. Если связь с реестром потеряна или аренда истекла, новые записи останавливаются.

При аварийном переключении поколение увеличивается. Поэтому восстановившийся старый регион со старым `epoch` не сможет возобновить запись автоматически. Этот механизм служит защитой от двух одновременно активных владельцев.

### 7.2. Доменные базы PostgreSQL

В каждом регионе сохраняются отдельные базы:

- Booking PostgreSQL;
- Driver PostgreSQL;
- Geography PostgreSQL;
- Pricing PostgreSQL;
- Payments PostgreSQL;
- Fraud PostgreSQL;
- Notification PostgreSQL.

Для каждой критичной доменной базы создаётся асинхронная межрегиональная реплика в парном регионе.

Направления:

- Сингапур → Джакарта;
- Джакарта → Сингапур;
- Сан-Паулу → Сантьяго;
- Сантьяго → Сан-Паулу.

При аварии резервные базы переводятся в режим записи только после перевода сегмента в состояние `FENCING`, увеличения поколения владения и подтверждения того, что старый регион больше не имеет действующей аренды записи.

### 7.3. Apache Kafka

Каждый регион имеет собственный Apache Kafka. Критичные доменные топики зеркалируются в парный регион через Kafka MirrorMaker 2.

Реплицируются:

- события Booking;
- бизнес-события Driver;
- события Pricing;
- события Payments;
- события Fraud;
- команды и результаты Saga;
- служебные события, необходимые для продолжения критического процесса.

Не требуется постоянно зеркалировать:

- высокочастотный `DriverLocationUpdated`;
- краткоживущие сигналы Flink;
- содержимое Redis.

После переключения координаты начинают поступать заново от водительских приложений, а потоковые сигналы пересчитываются.

### 7.4. Позиции потребителей Kafka

При аварийном восстановлении нельзя считать, что одинаковые числовые смещения в исходном и зеркальном топике обозначают одно и то же положение. MirrorMaker 2 настраивается на публикацию контрольных точек групп потребителей и перевод смещений в координаты зеркального кластера.

Для критичных групп перед открытием сегмента в резервном регионе выполняется следующая проверка:

1. получена последняя доступная контрольная точка группы;
2. смещение переведено в позицию зеркального топика;
3. потребитель стартует с этой позиции;
4. повторно доставленные сообщения безопасно отсеиваются по `event_id` через `inbox`.

Транзакционный исходящий журнал остаётся дополнительной страховкой. Если после повышения базы часть событий будет опубликована повторно, одинаковый `event_id` не должен привести к повторной бизнес-операции.

### 7.5. Redis и Elasticsearch

Оперативные хранилища Redis сохраняют тех же владельцев:

- Driver Redis;
- Pricing Redis;
- Geography Redis.

Elasticsearch остаётся индексом Geography.

Эти хранилища не являются источниками истины. После региональной аварии они восстанавливаются из доменных баз PostgreSQL и актуального потока событий.

## 8. Аварийное переключение

Диаграмма: [`failover.puml`](./failover.puml).

Для полного отказа Сингапура последовательность следующая:

1. проверки состояния фиксируют региональную деградацию и глобальный балансировщик перестаёт отправлять **новые операции** в Сингапур;
2. операции уже существующих сегментов `sg` временно не переводятся на запись в Джакарту, пока резервный контур не готов;
3. SRE подтверждает региональную аварию, а не кратковременный сбой отдельного сервиса;
4. в реестре владения сегмент `sg` переводится в состояние `FENCING`, его `epoch` увеличивается, выдача старых аренд записи прекращается;
5. проверяется фактическое отставание резервных доменных баз PostgreSQL и зеркал Kafka;
6. резервные доменные базы `sg` в Джакарте переводятся в режим записи;
7. критичные группы потребителей восстанавливают позиции по контрольным точкам MirrorMaker 2 и запускаются в Джакарте;
8. сервисы Джакарты проходят проверку записи в повышенные базы `sg`, состояния Kafka и зависимостей;
9. реестр переводит сегмент `sg` в состояние `ACTIVE`, `active_region=jkt` и выдаёт аренды нового поколения;
10. только после этого шлюзы начинают направлять операции существующих сегментов `sg` в Джакарту;
11. Redis прогреваются, индекс Geography перестраивается, координаты водителей начинают поступать заново;
12. выполняется сверка активных поездок, финансовых операций, состояния Saga и повторно доставленных событий.

Новые поездки пользователей из зоны Сингапура во время аварии могут сразу создаваться в Джакарте и получают `home_region=jkt`. Это позволяет не ждать повышения старых сегментов для новых операций.

### 8.1. Возврат после аварии

Восстановленный Сингапур не получает право записи автоматически.

Сначала:

1. все сервисы региона запускаются без аренды записи для сегмента `sg`;
2. старые базы не принимаются как источник истины;
3. регион синхронизируется от текущего владельца в Джакарте;
4. выполняется сверка данных и контрольных позиций Kafka;
5. при необходимости проводится отдельная плановая операция возврата;
6. только после смены `active_region`, увеличения `epoch` и получения новой аренды Сингапур снова получает право записи.

## 9. Сценарии отказа

| № | Отказ | Что происходит | Механизм восстановления | Целевой результат |
|---|---|---|---|---|
| **1** | Падение одного экземпляра сервиса | Теряется один экземпляр | Kubernetes перезапускает его, балансировка использует остальные | Без общей остановки |
| **2** | Потеря рабочего узла GKE | Реплики на узле недоступны | Планировщик запускает их на других узлах | Без регионального переключения |
| **3** | Отказ одной зоны региона | Часть региональных ресурсов недоступна | Региональный GKE и высокая доступность баз используют другие зоны | Регион остаётся активным |
| **4** | Отказ локального Kafka | Междоменные события временно не обрабатываются | Исходящий журнал сохраняет события; при длительном отказе критичные сегменты переводятся в парный регион | Без потери подтверждённых событий |
| **5** | Отказ одной доменной базы PostgreSQL внутри региона | Конкретный домен не может безопасно записывать данные | Внутрирегиональное переключение высокой доступности этой базы | Остальные домены продолжают работу |
| **6** | Полный отказ Сингапура | Сегменты `sg` теряют текущего владельца | Ограждение старого поколения → повышение реплик в Джакарте → восстановление Kafka → смена `active_region` | Выполнить АЦ-01 после подтверждения на учениях |
| **7** | Полный отказ Джакарты | Сегменты `jkt` теряют текущего владельца | Симметричное переключение в Сингапур | Выполнить АЦ-01 после подтверждения на учениях |
| **8** | Полный отказ Сан-Паулу | Сегменты `sao` теряют текущего владельца | Симметричное переключение в Сантьяго | Выполнить АЦ-01 после подтверждения на учениях |
| **9** | Полный отказ Сантьяго | Сегменты `scl` теряют текущего владельца | Симметричное переключение в Сан-Паулу | Выполнить АЦ-01 после подтверждения на учениях |
| **10** | Сетевой разрыв между парными регионами | Репликация останавливается, оба региона могут оставаться локально работоспособными | Каждый регион продолжает только свои активные сегменты; повышение чужих сегментов запрещено без процедуры ограждения | Не допустить двух владельцев записи |
| **11** | Недоступен реестр владения сегментами | Невозможно безопасно продлить аренду записи | Действующие аренды истекают; новые записи критичных сегментов останавливаются до восстановления реестра | Без расхождения владельцев |
| **12** | Ошибочная политика Cloud Armor | Легитимный трафик блокируется | Версионированная конфигурация и откат политики | Восстановление без изменения приложений |
| **13** | Потеря Redis | Теряется кэш и краткоживущее состояние | Восстановление из доменных данных и нового потока событий | Без потери источника истины |
| **14** | Потеря Elasticsearch Geography | Геопоиск временно деградирует | Перестроение индекса из Geography PostgreSQL и событий | Без потери бизнес-данных |

## 10. C2 и средства защиты

Доработанная схема: [`C2-global-deployment.puml`](./C2-global-deployment.puml).

Красным цветом отмечены новые элементы и связи глобального контура. Компоненты предыдущих архитектурных решений сохранены чёрными, чтобы была видна эволюция системы.

Добавляются:

- Cloud DNS;
- глобальный внешний балансировщик приложений;
- Cloud Armor;
- четыре региональных контура GKE;
- сетевой межсетевой экран VPC;
- Kubernetes NetworkPolicy;
- Cloud NAT;
- Secret Manager;
- Cloud KMS;
- глобальный реестр активного владельца сегмента;
- межрегиональные реплики доменных баз PostgreSQL;
- Kafka MirrorMaker 2.

### 10.1. Cloud Armor

Cloud Armor применяется как политика защиты глобального балансировщика, а не как самостоятельный сетевой промежуточный узел. Он используется для WAF-правил, ограничения частоты запросов и защиты от части DDoS-нагрузки до попадания запроса в региональный контур.

### 10.2. Сетевой межсетевой экран VPC

Региональные узлы приложения не должны быть доступны напрямую из интернета. Сетевые правила разрешают вход к региональному контуру только от глобального балансировщика и систем проверки состояния.

### 10.3. Kubernetes NetworkPolicy

Внутри регионального GKE сервисы получают только необходимые сетевые связи. Например, Payments не должен произвольно обращаться к базе Booking, а Notification — к базе Driver.

### 10.4. Исходящие интеграции

Cloud NAT обеспечивает исходящий доступ приватных узлов к внешним системам с предсказуемыми внешними адресами. Разрешённые направления соединений задаются сетевыми правилами, а не самим Cloud NAT.

Через этот контур выполняются вызовы:

- **платёжных шлюзов** — Яндекс Пэй и региональных поставщиков;
- **банковских программных интерфейсов** — для выплат водителям;
- **картографических сервисов** — Яндекс Карты и региональные поставщики;
- **поставщиков мобильных уведомлений** — FCM, APNS и Huawei Push Kit.

### 10.5. Секреты и ключи

Пароли, сертификаты и ключи внешних интеграций хранятся в Secret Manager. Ключи шифрования управляются через Cloud KMS и могут разделяться по регионам и юрисдикциям.

## 11. Стратегия соответствия локальным требованиям

Дополнительная часть решения строится на классификации данных и управляемом межрегиональном перемещении.

### 11.1. Классы данных

Выделяются как минимум:

1. персональные данные пассажира и водителя;
2. платёжные и банковские данные;
3. операционные данные поездки;
4. обезличенная аналитика и агрегаты.

### 11.2. Региональное владение

У записи есть `home_region`, а при необходимости — `data_jurisdiction`.

Если правила конкретной страны запрещают перенос определённого класса данных, такая информация:

- остаётся в разрешённой юрисдикции;
- не зеркалируется в запрещённый регион;
- для глобальной аналитики заменяется обезличенным или агрегированным представлением.

Схемы Сингапур ↔ Джакарта и Сан-Паулу ↔ Сантьяго являются базовой технической моделью, но политика репликации может быть строже для отдельных классов данных.

### 11.3. Дополнительные меры

- отдельные ключи шифрования по юрисдикциям;
- минимизация персональных данных в Kafka;
- маскирование персональных полей в журналах;
- отдельные сроки хранения по типам данных;
- журналирование административного доступа;
- регламентированное удаление данных;
- запрет межрегиональной репликации без явно разрешённой политики.

Перед запуском конкретной страны набор ограничений должен быть подтверждён юридической службой и службой информационной безопасности.

## 12. Мониторинг глобального контура

К существующему мониторингу добавляются:

- доступность каждого региона;
- задержка до выбранного региона;
- распределение трафика по регионам;
- состояние `active_region`, `epoch` и аренд владения;
- количество исключений региона из глобальной балансировки;
- отставание каждой межрегиональной доменной реплики PostgreSQL;
- отставание MirrorMaker 2;
- возраст последней контрольной точки групп потребителей;
- состояние зон и региональных GKE-кластеров;
- количество аварийных переключений;
- фактическое время восстановления;
- количество блокировок Cloud Armor;
- время прогрева Redis и перестроения индекса Geography.

Критическим считается состояние, когда парный регион недоступен одновременно с основным, истекают аренды владения или отставание резервной базы выходит за согласованные эксплуатационные пределы.

## 13. Альтернативы

### 13.1. Один регион на каждый континент

**Плюсы:** дешевле и проще.

**Минусы:** региональная авария требует межконтинентального переключения и увеличивает задержку.

**Решение:** отклонено.

### 13.2. Синхронная запись между регионами

**Плюсы:** минимальная потеря последних изменений.

**Минусы:** каждая операция зависит от межрегиональной задержки; сетевой разрыв может остановить запись сразу в двух регионах.

**Решение:** отклонено. Используется локальный владелец записи и асинхронная резервная реплика.

### 13.3. Один глобальный Kafka-кластер

**Плюсы:** единый журнал событий.

**Минусы:** высокая межконтинентальная задержка, более сложная локализация отказа и постоянный перенос высокочастотных координат.

**Решение:** отклонено. Используются региональные Kafka-кластеры и выборочное зеркалирование критичных топиков.

### 13.4. Полное зеркалирование Redis и Elasticsearch

**Плюсы:** быстрый старт резервного региона.

**Минусы:** усложнение согласованности для хранилищ, которые не являются источниками истины.

**Решение:** отклонено. Они восстанавливаются из доменных баз и событий.

### 13.5. Автоматическое повышение межрегиональной базы без ограждения старого региона

**Плюсы:** минимальное время переключения.

**Минусы:** при сетевом разделении возможно появление двух владельцев записи и трудноразрешимое расхождение данных.

**Решение:** отклонено. Право записи выдаётся только через поколение и короткоживущую аренду в реестре владения.

## 14. Компромиссы и риски

1. **Асинхронная межрегиональная репликация допускает потерю последних изменений при катастрофическом отказе.**  
   *Меры:* контролировать отставание, проверять его перед повышением реплики, использовать идемпотентность, зеркалирование событий и сверку после переключения.

2. **Четыре активных региона дороже одного или двух.**  
   *Меры:* независимое горизонтальное масштабирование и уменьшение мощностей вне пика.

3. **Переход с текущего облачного контура повышает сложность миграции.**  
   *Меры:* поэтапный перенос, единые контейнеры, инфраструктура как код и проверка до переключения трафика.

4. **Реестр владения становится критическим элементом управляющего контура.**  
   *Меры:* использовать глобально согласованное высокодоступное хранилище; при потере реестра записи прекращаются после истечения аренды, а чтение может продолжаться.

5. **Ошибочное переключение может создать двух владельцев записи.**  
   *Меры:* поколение владения, короткоживущая аренда, обязательное ограждение старого владельца и запрет автоматического возврата старого региона в запись.

6. **Одинаковая репликация не подходит всем странам.**  
   *Меры:* `data_jurisdiction` и явная политика разрешённых направлений репликации.
