# ADR-003: Глобальное развёртывание GoFuture

**Статус:** ✅ Принято  
**Участники:** Александр Вафин — автор решения; продуктовые команды GoFuture; платформенная команда; SRE-команда; инженеры данных; архитектурный комитет  
**Дата:** 2026-09-15

---

## 1. Контекст

GoFuture должен обеспечить доступность критических сервисов не ниже **99,99%** и низкую задержку для пользователей в Юго-Восточной Азии и Южной Америке. Для этого требуется работа более чем в трёх географических регионах, локальная обработка трафика, региональная отказоустойчивость, репликация критичных данных и формализованное аварийное переключение.

Task1 определил восемь доменных сервисов и правило владения данными:

- **Booking — сервис бронирования**;
- **Driver — сервис водителей**;
- **Pricing — сервис ценообразования**;
- **Payments — сервис платежей**;
- **Notification — сервис уведомлений**;
- **Geography — сервис географии**;
- **Analytics — сервис аналитики**;
- **Fraud — сервис защиты от мошенничества**.

Task2 добавил Apache Kafka, Apache Flink, Kafka Connect + Debezium, реестр схем, транзакционный исходящий журнал, оркестрационную Saga и единый контур наблюдаемости. Task3 не заменяет эти решения, а добавляет глобальную инфраструктуру поверх них.

**Шлюз программного интерфейса из Task1 и Task2 сохраняется.** В каждом регионе разворачивается его региональный экземпляр. Поэтому путь пользовательского запроса имеет вид:

`клиент → глобальный балансировщик → региональный шлюз программного интерфейса → доменный сервис`.

В исходном описании компании одновременно указаны Yandex Cloud и названия сервисов AWS. Для Task3 это архитектурно значимая неоднозначность, потому что целевые пользователи находятся в Юго-Восточной Азии и Южной Америке. В качестве целевого международного контура выбирается Google Cloud с регионами в обеих требуемых географиях. Существующее развёртывание в Yandex Cloud рассматривается как наследуемый контур на период миграции и не входит в критический путь целевой международной платформы.

## 2. Требования

### 2.1. Функциональные требования

| № | Требование |
|---|---|
| **ФТ-01** | Пользователь должен направляться в ближайший доступный регион без ручного выбора региона. |
| **ФТ-02** | При недоступности региона новый трафик должен автоматически перенаправляться в парный регион. |
| **ФТ-03** | Критичные данные каждого домена должны иметь резервную копию в другом регионе, пригодную для продолжения работы после аварии. |
| **ФТ-04** | Событийная платформа должна продолжать обработку критичных доменных событий после регионального отказа. |
| **ФТ-05** | Активная поездка и финансовая операция не должны одновременно изменяться двумя регионами как двумя независимыми владельцами записи. |
| **ФТ-06** | Внешний трафик должен проходить через средства защиты до попадания в региональные сервисы. |
| **ФТ-07** | Аварийное переключение должно иметь условия запуска, порядок действий и критерии возврата. |
| **ФТ-08** | Для каждого региона должны собираться метрики доступности, задержки и отставания репликации. |

### 2.2. Нефункциональные требования из задания

| № | Категория | Требование | Критичность |
|---|---|---|---|
| **НФТ-01** | Доступность | Доступность критических пользовательских сервисов должна быть не ниже **99,99%**. | Критичная |
| **НФТ-02** | География | Рабочий контур должен быть развёрнут **более чем в трёх географических регионах**. | Критичная |
| **НФТ-03** | Задержка | Пользователь должен обслуживаться ближайшим подходящим регионом, чтобы снизить сетевую задержку. | Критичная |
| **НФТ-04** | Отказоустойчивость | Архитектура должна переживать отказ зоны и иметь механизм продолжения работы при отказе целого региона. | Критичная |
| **НФТ-05** | Безопасность | Публичный контур должен быть защищён WAF, сетевым межсетевым экраном и дополнительными сетевыми ограничениями. | Критичная |
| **НФТ-06** | Регуляторные требования | Архитектура должна позволять ограничить хранение и передачу данных допустимой юрисдикцией. | Высокая |

### 2.3. Архитектурные целевые показатели решения

Следующие значения **не заданы заказчиком в исходном задании**. Это принятые в данном ADR эксплуатационные цели, которые должны быть подтверждены нагрузочными испытаниями и учениями по аварийному восстановлению:

| № | Показатель | Целевое значение |
|---|---|---|
| **АЦ-01** | Время восстановления критического контура при отказе региона | не более 10 минут |
| **АЦ-02** | Отставание межрегиональной реплики критичной PostgreSQL в штатном режиме | желательно не более 60 секунд |
| **АЦ-03** | Потеря данных при катастрофическом отказе региона | не больше фактического отставания асинхронной реплики |

## 3. Согласованность с Task1 и Task2

Task3 сохраняет следующие ранее принятые решения:

1. Каждый доменный сервис владеет своей PostgreSQL.
2. Прямой доступ к базе другого домена запрещён.
3. Оперативные хранилища Redis логически разделены между Driver, Pricing и Geography.
4. Elasticsearch является геопоисковым индексом Geography, а не общей междоменной базой.
5. Apache Kafka остаётся основным журналом междоменных событий.
6. Kafka Connect + Debezium публикует события из транзакционных исходящих журналов.
7. Apache Flink выполняет потоковые вычисления.
8. Шлюз программного интерфейса остаётся общей точкой входа в доменные программные интерфейсы.
9. Prometheus, Grafana, Alertmanager, Loki, OpenTelemetry, Jaeger и экспортёры сохраняются как контур наблюдаемости.

C2 Task3 построена именно как развитие C2 Task2: базовые компоненты показаны без красного выделения, а новые инфраструктурные элементы Task3 отмечены красным.

## 4. Выбор регионов

Для целевого контура выбираются четыре региона Google Cloud:

| География | Регион | Внутренний идентификатор GoFuture | Код Google Cloud | Роль |
|---|---|---|---|---|
| Юго-Восточная Азия | **Сингапур** | `sg` | `asia-southeast1` | Активный регион, парный резерв для Джакарты |
| Юго-Восточная Азия | **Джакарта** | `jkt` | `asia-southeast2` | Активный регион, парный резерв для Сингапура |
| Южная Америка | **Сан-Паулу** | `sao` | `southamerica-east1` | Активный регион, парный резерв для Сантьяго |
| Южная Америка | **Сантьяго** | `scl` | `southamerica-west1` | Активный регион, парный резерв для Сан-Паулу |

### 4.1. Почему используются отдельные внутренние идентификаторы

Коды `sg`, `jkt`, `sao`, `scl` принадлежат модели GoFuture и не зависят от конкретного облачного провайдера. Поэтому события и топики Kafka не связываются с кодами Google Cloud.

Примеры:

- `gofuture.sg.booking.events.v1`;
- `gofuture.jkt.booking.events.v1`;
- `gofuture.sao.booking.events.v1`;
- `gofuture.scl.booking.events.v1`.

Если в будущем физический регион или облачный провайдер изменится, контракт событийной платформы менять не потребуется.

### 4.2. Обоснование выбора

**Сингапур** используется как один из основных узлов Юго-Восточной Азии и образует пару аварийного восстановления с Джакартой.

**Джакарта** является отдельным активным регионом для Индонезии и соседнего трафика, а не только резервной площадкой.

**Сан-Паулу** обслуживает Бразилию и восточную часть Южной Америки.

**Сантьяго** обслуживает западную часть континента и является парным регионом для Сан-Паулу.

Такой выбор даёт четыре рабочих региона в двух целевых географиях. При отказе одного региона переключение сначала выполняется внутри того же макрорегиона, без межконтинентального перехода.

### 4.3. Почему целевой международный контур не остаётся только в Yandex Cloud

Для выполнения Task3 нужны физические регионы в Юго-Восточной Азии и Южной Америке. Текущий контур Yandex Cloud может использоваться на этапе миграции, но не решает требование низкой задержки для указанных рынков.

Переход на Google Cloud повышает стоимость миграции и требует новых эксплуатационных компетенций. Этот компромисс принимается ради выполнения требований по географии, задержке и региональной отказоустойчивости.

## 5. Региональная модель развёртывания

В каждом из четырёх регионов разворачивается одинаковый набор критических компонентов:

1. региональный кластер GKE в нескольких зонах;
2. региональный экземпляр **шлюза программного интерфейса**;
3. Booking, Driver, Geography, Pricing, Payments, Fraud, Notification и Analytics;
4. отдельные доменные PostgreSQL;
5. оперативные хранилища Redis доменов Driver, Pricing и Geography;
6. геопоисковый индекс Elasticsearch домена Geography;
7. локальный Apache Kafka;
8. реестр схем;
9. Kafka Connect + Debezium;
10. локальный Apache Flink и хранилище его контрольных точек;
11. средства наблюдаемости из Task2.

Отказ одной зоны закрывается внутри регионального GKE-кластера и региональной схемы высокой доступности баз. Перенос в другой географический регион выполняется только при региональной аварии или длительной недоступности критического пути.

Горизонтальное масштабирование сервисов выполняется независимо по регионам. Для сервисов и потребителей Kafka учитываются не только ЦП и память, но также задержка, длина очереди и отставание потребителей.

## 6. Географическая маршрутизация

Схема: [`geo-routing.puml`](./geo-routing.puml).

Путь запроса:

1. клиент обращается к единому имени GoFuture;
2. Cloud DNS возвращает адрес глобального внешнего балансировщика;
3. Cloud Armor применяется как политика защиты входящего трафика;
4. глобальный балансировщик выбирает ближайший здоровый регион с допустимым размещением данных и достаточной ёмкостью;
5. запрос передаётся в региональный **шлюз программного интерфейса**;
6. шлюз маршрутизирует запрос в нужный доменный сервис.

Парные регионы:

- Сингапур (`sg`) ↔ Джакарта (`jkt`);
- Сан-Паулу (`sao`) ↔ Сантьяго (`scl`).

При отказе региона предпочтение отдаётся его паре внутри того же макрорегиона. Межконтинентальное переключение допускается только как крайняя мера и только если это разрешают правила размещения данных.

Проверка готовности региона должна отражать не только доступность HTTP-процесса, но и возможность выполнить критический бизнес-путь. Например, для Booking недостаточно вернуть `200 OK`, если недоступна его PostgreSQL или критичная событийная инфраструктура.

## 7. Репликация данных

Схема: [`data-replication.puml`](./data-replication.puml).

### 7.1. Один владелец записи

Каждая операционная сущность имеет `region_owner` со значением `sg`, `jkt`, `sao` или `scl`.

Например, поездка с `region_owner=sg` изменяется только сервисами региона Сингапур. Её резервные копии в Джакарте до аварийного переключения не являются независимым владельцем записи.

Такой подход позволяет избежать синхронной межрегиональной транзакции и конфликта двух основных экземпляров.

### 7.2. Доменные PostgreSQL

Важно: выражение «доменные PostgreSQL региона» **не означает одну общую базу**. В каждом регионе сохраняются отдельные базы:

- Booking PostgreSQL;
- Driver PostgreSQL;
- Geography PostgreSQL;
- Pricing PostgreSQL;
- Payments PostgreSQL;
- Fraud PostgreSQL;
- Notification PostgreSQL.

Для каждой критичной доменной базы создаётся асинхронная межрегиональная реплика в парном регионе.

Направления:

- Сингапур → Джакарта;
- Джакарта → Сингапур;
- Сан-Паулу → Сантьяго;
- Сантьяго → Сан-Паулу.

При аварии резервные базы переводятся в режим записи только после блокировки старого владельца.

### 7.3. Apache Kafka

Каждый регион имеет собственный Apache Kafka. Критичные доменные топики зеркалируются в парный регион через Kafka MirrorMaker 2.

Реплицируются:

- события Booking;
- бизнес-события Driver;
- события Pricing;
- события Payments;
- события Fraud;
- команды и результаты Saga;
- служебные события, необходимые для продолжения критического процесса.

Не требуется постоянно зеркалировать:

- высокочастотный `DriverLocationUpdated`;
- краткоживущие сигналы Flink;
- содержимое Redis.

После переключения координаты начинают поступать заново от водительских приложений, а потоковые сигналы пересчитываются.

### 7.4. Redis и Elasticsearch

Оперативные хранилища Redis сохраняют тех же владельцев, что и в Task1:

- Driver Redis;
- Pricing Redis;
- Geography Redis.

Elasticsearch остаётся индексом Geography.

Эти хранилища не являются источниками истины. После региональной аварии они восстанавливаются из доменных PostgreSQL и событий.

## 8. Аварийное переключение

Диаграмма: [`failover.puml`](./failover.puml).

При полной потере региона выполняются следующие действия:

1. проверки готовности исключают неисправный регион из новых подключений;
2. глобальный балансировщик направляет новые запросы в парный регион;
3. SRE подтверждает, что наблюдается региональная авария, а не кратковременная локальная проблема;
4. проверяется фактическое отставание резервных доменных PostgreSQL;
5. старый регион блокируется как владелец записи;
6. резервные доменные PostgreSQL в парном регионе переводятся в режим записи;
7. критичные Kafka-топики продолжаются из зеркала MirrorMaker 2;
8. Saga и доменные потребители возобновляют работу;
9. Redis прогреваются, индекс Geography перестраивается, координаты водителей начинают поступать заново;
10. выполняется проверка активных поездок, финансовых операций и состояния Saga.

Автоматически выполняются проверки готовности, исключение региона из балансировки и маршрутизация нового трафика. Перевод резервных PostgreSQL в режим записи требует подтверждённой региональной аварии. Это снижает риск появления двух владельцев одной и той же записи.

### 8.1. Возврат после аварии

Восстановленный старый регион не получает право записи автоматически.

Сначала он подключается как резерв, синхронизируется с текущим владельцем и проходит сверку. Возврат роли владельца выполняется отдельной плановой операцией.

## 9. Сценарии отказа

| № | Отказ | Что происходит | Механизм восстановления | Целевой результат |
|---|---|---|---|---|
| **1** | Падение одного экземпляра сервиса | Теряется один экземпляр | Kubernetes перезапускает его, балансировка использует остальные | Без общей остановки |
| **2** | Потеря рабочего узла GKE | Реплики на узле недоступны | Планировщик запускает их на других узлах | Без регионального переключения |
| **3** | Отказ одной зоны региона | Часть региональных ресурсов недоступна | Региональный GKE и высокая доступность баз используют другие зоны | Регион остаётся активным |
| **4** | Отказ локального Kafka | Междоменные события не обрабатываются | Outbox сохраняет события; при длительном отказе критичный трафик переносится в парный регион | Без потери подтверждённых событий |
| **5** | Отказ одной доменной PostgreSQL внутри региона | Конкретный домен не может безопасно записывать данные | Внутрирегиональное переключение высокой доступности этой базы | Остальные домены не обязаны останавливаться |
| **6** | Полный отказ Сингапура | Сегменты `sg` недоступны в основном регионе | Трафик → Джакарта, резервные доменные базы `sg` переводятся в запись | Выполнить АЦ-01 после подтверждения на учениях |
| **7** | Полный отказ Джакарты | Сегменты `jkt` недоступны | Симметричное переключение → Сингапур | Выполнить АЦ-01 после подтверждения на учениях |
| **8** | Полный отказ Сан-Паулу | Сегменты `sao` недоступны | Переключение → Сантьяго | Выполнить АЦ-01 после подтверждения на учениях |
| **9** | Полный отказ Сантьяго | Сегменты `scl` недоступны | Переключение → Сан-Паулу | Выполнить АЦ-01 после подтверждения на учениях |
| **10** | Ошибочная политика Cloud Armor | Легитимный трафик блокируется | Версионированная конфигурация и откат политики | Восстановление без изменения приложений |
| **11** | Потеря Redis | Теряется кэш и краткоживущее состояние | Восстановление из доменных данных и нового потока событий | Без потери источника истины |
| **12** | Потеря Elasticsearch Geography | Геопоиск временно деградирует | Перестроение индекса из Geography PostgreSQL и событий | Без потери бизнес-данных |

## 10. C2 и средства защиты

Доработанная схема: [`C2-global-deployment.puml`](./C2-global-deployment.puml).

**Красным цветом отмечены только новые элементы и связи Task3.** Компоненты Task1 и Task2 сохранены чёрными, чтобы было видно эволюцию архитектуры.

Добавляются:

- Cloud DNS;
- глобальный внешний балансировщик приложений;
- Cloud Armor;
- четыре региональных контура GKE;
- сетевой межсетевой экран VPC;
- Kubernetes NetworkPolicy;
- Cloud NAT;
- Secret Manager;
- Cloud KMS;
- межрегиональные реплики доменных PostgreSQL;
- Kafka MirrorMaker 2.

### 10.1. Cloud Armor

Cloud Armor применяется как политика защиты глобального балансировщика, а не как самостоятельный сетевой промежуточный узел. Он используется для WAF-правил, ограничения частоты запросов и защиты от части DDoS-нагрузки до попадания запроса в региональный контур.

### 10.2. Сетевой межсетевой экран VPC

Региональные узлы приложения не должны быть доступны напрямую из интернета. Сетевые правила разрешают вход к региональному контуру только от глобального балансировщика и систем проверки состояния.

### 10.3. Kubernetes NetworkPolicy

Внутри регионального GKE сервисы получают только необходимые сетевые связи. Например, Payments не должен произвольно обращаться к базе Booking, а Notification — к базе Driver.

### 10.4. Исходящие интеграции

Через контролируемый Cloud NAT выполняются вызовы следующих внешних категорий:

- **платёжные шлюзы** — Яндекс Пэй и региональные поставщики;
- **банковские программные интерфейсы** — выплаты водителям;
- **картографические сервисы** — Яндекс Карты и региональные поставщики;
- **поставщики мобильных уведомлений** — FCM, APNS и Huawei Push Kit.

Так сохраняются внешние интеграции из Task1 и Task2, но появляется возможность подменять поставщика в зависимости от страны.

### 10.5. Секреты и ключи

Пароли, сертификаты и ключи внешних интеграций хранятся в Secret Manager. Ключи шифрования управляются через Cloud KMS и могут разделяться по регионам и юрисдикциям.

## 11. Стратегия соответствия локальным требованиям

Дополнительная часть задания реализуется через классификацию данных и управляемое межрегиональное перемещение.

### 11.1. Классы данных

Выделяются как минимум:

1. персональные данные пассажира и водителя;
2. платёжные и банковские данные;
3. операционные данные поездки;
4. обезличенная аналитика и агрегаты.

### 11.2. Региональное владение

У записи есть `region_owner`, а при необходимости — `data_jurisdiction`.

Если правила конкретной страны запрещают перенос определённого класса данных, такая информация:

- остаётся в разрешённой юрисдикции;
- не зеркалируется в запрещённый регион;
- для глобальной аналитики заменяется обезличенным или агрегированным представлением.

Схемы Сингапур ↔ Джакарта и Сан-Паулу ↔ Сантьяго являются базовой технической моделью, но политика репликации может быть строже для отдельных классов данных.

### 11.3. Дополнительные меры

- отдельные ключи шифрования по юрисдикциям;
- минимизация персональных данных в Kafka;
- маскирование персональных полей в журналах;
- отдельные сроки хранения по типам данных;
- журналирование административного доступа;
- регламентированное удаление данных;
- запрет межрегиональной репликации без явно разрешённой политики.

Перед запуском конкретной страны набор ограничений должен быть подтверждён юридической и информационной безопасностью.

## 12. Мониторинг глобального контура

К мониторингу из Task2 добавляются:

- доступность каждого региона;
- задержка до выбранного региона;
- распределение трафика по регионам;
- количество исключений региона из глобальной балансировки;
- отставание каждой межрегиональной доменной PostgreSQL-реплики;
- отставание MirrorMaker 2;
- состояние зон и региональных GKE-кластеров;
- количество аварийных переключений;
- фактическое время восстановления;
- количество блокировок Cloud Armor;
- время прогрева Redis и перестроения индекса Geography.

Критическим считается состояние, когда парный регион недоступен одновременно с основным либо отставание резервной базы выходит за согласованные эксплуатационные пределы.

## 13. Альтернативы

### 13.1. Один регион на каждый континент

**Плюсы:** дешевле и проще.

**Минусы:** региональная авария требует межконтинентального переключения и увеличивает задержку.

**Решение:** отклонено.

### 13.2. Синхронная запись между регионами

**Плюсы:** минимальная потеря последних изменений.

**Минусы:** каждая операция зависит от межрегиональной задержки; сетевой разрыв может остановить запись сразу в двух регионах.

**Решение:** отклонено. Используется локальный владелец записи и асинхронная резервная реплика.

### 13.3. Один глобальный Kafka-кластер

**Плюсы:** единый журнал событий.

**Минусы:** высокая межконтинентальная задержка, более сложная локализация отказа и постоянный перенос высокочастотных координат.

**Решение:** отклонено. Используются региональные Kafka-кластеры и выборочное зеркалирование критичных топиков.

### 13.4. Полное зеркалирование Redis и Elasticsearch

**Плюсы:** быстрый старт резервного региона.

**Минусы:** усложнение согласованности для хранилищ, которые не являются источниками истины.

**Решение:** отклонено. Они восстанавливаются из доменных баз и событий.

## 14. Компромиссы и риски

1. **Асинхронная межрегиональная репликация допускает потерю последних изменений при катастрофическом отказе.**  
   *Меры:* контролировать лаг, проверять его перед переводом реплики в запись, использовать идемпотентность и журнал событий.

2. **Четыре активных региона дороже одного или двух.**  
   *Меры:* независимое горизонтальное масштабирование и уменьшение мощностей вне пика.

3. **Переход с текущего облачного контура повышает сложность миграции.**  
   *Меры:* поэтапный перенос, единые контейнеры, Infrastructure as Code и проверка до переключения трафика.

4. **Ошибочное переключение может создать двух владельцев записи.**  
   *Меры:* обязательная блокировка старого владельца и запрет автоматического возврата старого региона в запись.

5. **Одинаковая репликация не подходит всем странам.**  
   *Меры:* `data_jurisdiction` и явная политика разрешённых направлений репликации.

## 15. Критерии завершения Task3

Task3 считается завершённым, когда:

- обоснован выбор четырёх регионов;
- зафиксированы внутренние идентификаторы регионов, не зависящие от облачного провайдера;
- определена репликация отдельных доменных PostgreSQL;
- описано выборочное зеркалирование Kafka;
- определена географическая маршрутизация через глобальный балансировщик и региональный шлюз программного интерфейса;
- C2 является развитием C2 Task2, а новые элементы Task3 выделены красным;
- показаны WAF, VPC Firewall, NetworkPolicy, Cloud NAT, Secret Manager и KMS;
- создана C4 Deployment-диаграмма аварийного переключения;
- составлена таблица сценариев отказа;
- отдельно обозначены архитектурные цели по времени восстановления и допустимой потере данных;
- описана стратегия ограничения данных по юрисдикциям.
