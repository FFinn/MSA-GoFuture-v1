# Задание 3. Обеспечиваем высокую нагрузку

В этом задании спроектировано глобальное развёртывание GoFuture для доступности 99,99% и низкой задержки в Юго-Восточной Азии и Южной Америке.

## Артефакты

- [`ADR-003-global-deployment.md`](./ADR-003-global-deployment.md) — выбор регионов, модель глобального развёртывания, владение сегментами, аварийное переключение, таблица сценариев отказа, средства защиты, риски и стратегия ограничения данных по юрисдикциям.
- [`C2-global-deployment.puml`](./C2-global-deployment.puml) — C2 глобального контура. Компоненты предыдущих архитектурных решений сохранены, а новые элементы задания 3 выделены красным.
- [`data-replication.puml`](./data-replication.puml) — схема репликации отдельных доменных баз PostgreSQL и критичных Kafka-топиков между парными регионами.
- [`geo-routing.puml`](./geo-routing.puml) — схема географической маршрутизации новых операций и маршрутизации существующих сущностей по текущему владельцу сегмента.
- [`failover.puml`](./failover.puml) — C4-диаграмма развёртывания аварийного переключения на примере Сингапур → Джакарта; для Сан-Паулу ↔ Сантьяго применяется тот же механизм.

## Выбранные регионы

Целевой международный контур разворачивается в четырёх регионах Google Cloud:

- Сингапур — внутренний идентификатор `sg`, Google Cloud `asia-southeast1`;
- Джакарта — внутренний идентификатор `jkt`, Google Cloud `asia-southeast2`;
- Сан-Паулу — внутренний идентификатор `sao`, Google Cloud `southamerica-east1`;
- Сантьяго — внутренний идентификатор `scl`, Google Cloud `southamerica-west1`.

Внутренние идентификаторы GoFuture не зависят от поставщика облачной инфраструктуры и используются как устойчивые обозначения домашних сегментов данных и в именах региональных Kafka-топиков.

Регионы образуют две пары аварийного восстановления: Сингапур ↔ Джакарта и Сан-Паулу ↔ Сантьяго. Оба региона каждой пары штатно активны, но обслуживают разные домашние сегменты.

## Основные решения

Для **новой** операции глобальный балансировщик выбирает ближайший здоровый регион с достаточной ёмкостью и допустимым размещением данных. Созданная сущность получает неизменяемый `home_region`.

Для **существующей** поездки ближайший регион заново не выбирается. Региональный шлюз определяет домашний сегмент сущности и обращается к реестру активного владельца, где хранится соответствие `home_region → active_region`, поколение владения и состояние сегмента. При аварии меняется `active_region`, но `home_region` бизнес-сущности остаётся прежним.

Для PostgreSQL сохраняется принцип «один домен — одна база». Для каждой критичной доменной базы создаётся асинхронная резервная реплика в парном регионе. После переключения сервис выбирает базу своего домена по `home_region` запроса. Например, Booking в Джакарте может работать со своей базой сегмента `jkt` и с повышенной резервной базой Booking сегмента `sg`, не обращаясь к базам других доменов.

Право записи защищено поколением `epoch` и короткоживущей арендой. При региональной аварии сначала прекращается право записи старого поколения, затем повышаются резервные базы и восстанавливаются потребители Kafka, и только после проверки готовности меняется `active_region` и открывается запись пользовательского трафика.

Каждый регион имеет собственный Apache Kafka. MirrorMaker 2 зеркалирует критичные бизнес-события и контрольные точки групп потребителей. После переключения потребители восстанавливают позиции по этим контрольным точкам; повторная доставка безопасна благодаря `event_id`, `inbox` и идемпотентной обработке.

Высокочастотные координаты водителей, краткоживущие сигналы Flink и содержимое Redis постоянно между регионами не копируются: они восстанавливаются после переключения.

Cloud NAT используется для исходящего доступа приватных узлов с предсказуемыми внешними адресами. Разрешённые направления определяются сетевыми правилами. Внешние интеграции сохраняют четыре категории: платёжные шлюзы, банковские программные интерфейсы для выплат, картографические сервисы и поставщики мобильных уведомлений.

Целевые значения времени восстановления до 10 минут и штатного отставания резервной базы до 60 секунд обозначены в ADR как **архитектурные цели решения**, а не как требования из условия.

На диаграммах **красным цветом выделены изменения задания 3**.
