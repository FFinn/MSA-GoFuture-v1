# Task3. Обеспечиваем высокую нагрузку

В этом задании спроектировано глобальное развёртывание GoFuture для доступности 99,99% и низкой задержки в Юго-Восточной Азии и Южной Америке.

## Артефакты

- [`ADR-003-global-deployment.md`](./ADR-003-global-deployment.md) — выбор регионов, модель глобального развёртывания, аварийное переключение, таблица сценариев отказа, средства защиты, риски и стратегия ограничения данных по юрисдикциям.
- [`C2-global-deployment.puml`](./C2-global-deployment.puml) — доработанная C2 из Task2. Компоненты предыдущих заданий сохранены, а новые элементы Task3 выделены красным.
- [`data-replication.puml`](./data-replication.puml) — схема репликации отдельных доменных PostgreSQL и критичных Kafka-топиков между парными регионами.
- [`geo-routing.puml`](./geo-routing.puml) — схема географической маршрутизации пользователей через глобальный балансировщик в региональный шлюз программного интерфейса.
- [`failover.puml`](./failover.puml) — C4 Deployment-диаграмма аварийного переключения на примере Сингапур → Джакарта; для Сан-Паулу ↔ Сантьяго применяется тот же механизм.

## Выбранные регионы

Целевой международный контур разворачивается в четырёх регионах Google Cloud:

- Сингапур — внутренний идентификатор `sg`, Google Cloud `asia-southeast1`;
- Джакарта — внутренний идентификатор `jkt`, Google Cloud `asia-southeast2`;
- Сан-Паулу — внутренний идентификатор `sao`, Google Cloud `southamerica-east1`;
- Сантьяго — внутренний идентификатор `scl`, Google Cloud `southamerica-west1`.

Внутренние идентификаторы GoFuture не зависят от облачного провайдера и используются в `region_owner` и именах региональных Kafka-топиков.

Регионы образуют две пары аварийного восстановления: Сингапур ↔ Джакарта и Сан-Паулу ↔ Сантьяго. Оба региона каждой пары штатно активны, но являются владельцами разных сегментов данных.

## Согласованность с Task1 и Task2

В Task3 сохранены ранее принятые компоненты и границы:

- `Booking — сервис бронирования`;
- `Driver — сервис водителей`;
- `Pricing — сервис ценообразования`;
- `Payments — сервис платежей`;
- `Notification — сервис уведомлений`;
- `Geography — сервис географии`;
- `Analytics — сервис аналитики`;
- `Fraud — сервис защиты от мошенничества`;
- шлюз программного интерфейса;
- отдельные PostgreSQL каждого домена;
- Redis доменов Driver, Pricing и Geography;
- Elasticsearch домена Geography;
- Apache Kafka, Kafka Connect + Debezium, Apache Flink и реестр схем;
- Prometheus, Grafana, Alertmanager, Loki, OpenTelemetry и Jaeger.

## Ключевые решения

Пользовательский трафик проходит через Cloud Armor и глобальный внешний балансировщик приложений. Балансировщик выбирает ближайший здоровый регион с достаточной ёмкостью и допустимым размещением данных. После этого запрос попадает в региональный экземпляр **шлюза программного интерфейса**, а уже он маршрутизирует запрос к доменным сервисам.

Для PostgreSQL сохраняется принцип «один домен — одна база». В каждом регионе есть отдельные Booking PostgreSQL, Driver PostgreSQL, Geography PostgreSQL и другие доменные базы. Для каждой критичной доменной базы создаётся асинхронная резервная реплика в парном регионе. Резерв не переводится в режим записи, пока старый владелец не заблокирован.

Каждый регион имеет собственный Apache Kafka. MirrorMaker 2 зеркалирует в парный регион только критичные бизнес-события. Высокочастотные координаты водителей, краткоживущие сигналы Flink и содержимое Redis постоянно между регионами не копируются: они восстанавливаются после переключения.

Внешние интеграции сохраняют категории из предыдущих заданий: платёжные шлюзы, банковские программные интерфейсы для выплат, картографические сервисы и поставщики мобильных уведомлений.

Целевые значения времени восстановления до 10 минут и отставания резервной базы до 60 секунд обозначены в ADR как **архитектурные цели решения**, а не как требования, заданные в условии.

На диаграммах **красным цветом выделены изменения Task3**, чтобы их можно было быстро отличить от компонентов, принятых в Task1 и Task2.
