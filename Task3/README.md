# Task3. Обеспечиваем высокую нагрузку

В этом задании спроектировано глобальное развёртывание GoFuture для доступности 99,99% и низкой задержки в Юго-Восточной Азии и Южной Америке.

## Артефакты

- [`ADR-003-global-deployment.md`](./ADR-003-global-deployment.md) — выбор регионов, модель глобального развёртывания, аварийное переключение, таблица сценариев отказа, средства защиты, риски и стратегия ограничения данных по юрисдикциям.
- [`C2-global-deployment.puml`](./C2-global-deployment.puml) — доработанная C2 с глобальным балансировщиком, Cloud Armor, региональными GKE-кластерами, сетевой защитой и межрегиональной репликацией.
- [`data-replication.puml`](./data-replication.puml) — схема репликации PostgreSQL и критичных Kafka-топиков между парными регионами.
- [`geo-routing.puml`](./geo-routing.puml) — схема географической маршрутизации пользователей в ближайший здоровый регион.
- [`failover.puml`](./failover.puml) — C4 Deployment-диаграмма аварийного переключения на примере Singapore → Jakarta; для São Paulo ↔ Santiago применяется тот же механизм.

## Выбранные регионы

Целевой международный контур разворачивается в четырёх регионах Google Cloud:

- Singapore — `asia-southeast1`;
- Jakarta — `asia-southeast2`;
- São Paulo — `southamerica-east1`;
- Santiago — `southamerica-west1`.

Регионы образуют две пары аварийного восстановления: Singapore ↔ Jakarta и São Paulo ↔ Santiago. Оба региона каждой пары штатно активны, но являются владельцами разных сегментов данных.

## Ключевые решения

Пользовательский трафик проходит через Cloud Armor и глобальный внешний балансировщик приложений. Балансировщик выбирает ближайший здоровый регион с достаточной ёмкостью. При отказе региона новый трафик автоматически переносится в его пару того же макрорегиона.

Для PostgreSQL используется один владелец записи и асинхронная межрегиональная реплика. Резервная база не переводится в режим записи, пока старый владелец не заблокирован. Это защищает от ситуации, когда два региона одновременно считают себя основными.

Каждый регион имеет собственный Kafka. MirrorMaker 2 зеркалирует в парный регион только критичные бизнес-события. Высокочастотные координаты водителей, краткоживущие сигналы Flink, Redis и Elasticsearch между регионами постоянно не копируются: они восстанавливаются после переключения.

На всех диаграммах **красным цветом выделены изменения Task3**, чтобы их можно было быстро отличить от решений предыдущих заданий.
