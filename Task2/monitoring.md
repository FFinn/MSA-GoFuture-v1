# Мониторинг событийной платформы GoFuture

Этот документ дополняет [`ADR-002-event-driven-architecture.md`](./ADR-002-event-driven-architecture.md) и фиксирует именно эксплуатационный контур Task2: что контролируем, какими инструментами и какие показатели считаем критичными.

## 1. Подход к мониторингу

Для прикладных сервисов используется метод **RED**:

- **Rate** — скорость обработки запросов и событий;
- **Errors** — количество и доля ошибок;
- **Duration** — длительность обработки.

Для событийной платформы этого недостаточно. Kafka и Flink могут формально оставаться доступными, но при этом накапливать отставание и перестать обеспечивать обработку в реальном времени. Поэтому дополнительно контролируются:

- состояние брокеров и репликации Kafka;
- отставание групп потребителей;
- возраст самого старого необработанного события;
- состояние заданий Flink и контрольных точек;
- обратное давление потоковых операторов;
- доставка Outbox → Kafka;
- состояние Saga и сроки выполнения её шагов.

Метрики рассматриваются отдельно по регионам. Усреднение по всей платформе недопустимо: нормальная работа двух регионов не должна скрывать деградацию третьего.

## 2. Инструменты

| Инструмент | Что контролирует | Как используется |
|---|---|---|
| **Prometheus** | Сервисы, Kafka, Flink, Kafka Connect/Debezium, Saga | Основное хранилище числовых метрик |
| **Grafana** | Все метрики и журналы | Панели по регионам, доменам, группам потребителей и Saga |
| **Alertmanager** | Сработавшие правила Prometheus | Маршрутизация оповещений SRE и ответственным командам |
| **Loki** | Журналы сервисов, потребителей, Flink и Kafka Connect | Поиск ошибок по `event_id`, `correlation_id` и `saga_id` |
| **Kafka Exporter** | Отставание групп потребителей, состояние топиков | Метрики потребителей Kafka |
| **JMX Exporter** | Брокеры Kafka и Kafka Connect | Технические метрики JVM, брокеров и соединителей |
| **Flink Prometheus Reporter** | Потоковые задания Flink | Метрики обработки, контрольных точек и обратного давления |
| **OpenTelemetry Collector** | Трассы межсервисных операций | Сбор распределённых трасс |
| **Jaeger** | Распределённые трассы | Разбор конкретной поездки и Saga по идентификаторам |
| **PostgreSQL Exporter** | Доменные PostgreSQL | Соединения, блокировки, задержки и состояние баз |

Все перечисленные инструменты отражены на диаграмме [`C2-event-platform.puml`](./C2-event-platform.puml).

## 3. Метрики Kafka

### 3.1. Брокеры

- скорость поступления сообщений;
- скорость выдачи сообщений;
- входящий и исходящий сетевой поток;
- использование диска;
- количество недоступных партиций;
- количество партиций с неполным числом синхронных реплик;
- частота уменьшения и восстановления ISR;
- длительность обработки запросов produce/fetch;
- загрузка обработчиков сетевых и дисковых запросов;
- число активных брокеров.

Критическими считаются ситуации, когда появляется хотя бы одна недоступная партиция критичного топика или длительно сохраняется неполный набор синхронных реплик.

### 3.2. Группы потребителей

Для каждой группы потребителей и каждого региона собираются:

- текущее отставание в сообщениях;
- отставание во времени;
- максимальное отставание по одной партиции;
- скорость уменьшения/роста отставания;
- количество активных потребителей;
- количество перебалансировок группы;
- скорость обработки сообщений.

Главный показатель — не абсолютное число сообщений в очереди, а **растёт ли отставание и нарушает ли оно допустимое время доставки события**.

Для `driver.location` и потоков ценообразования допустимое отставание должно быть значительно меньше, чем для аналитического потребителя. Конкретные числовые пороги определяются по результатам нагрузочных испытаний и закрепляются как целевые показатели уровня обслуживания.

## 4. Метрики Flink

Для каждого задания Flink контролируются:

- состояние задания;
- количество входящих и исходящих записей;
- число обработанных записей в секунду;
- занятость операторов;
- обратное давление;
- длительность контрольной точки;
- количество успешных и неуспешных контрольных точек;
- время с последней успешной контрольной точки;
- количество перезапусков задания;
- размер состояния;
- отставание водяного знака от текущего времени;
- число отброшенных или ошибочных записей.

Отдельная панель должна показывать путь `DriverLocationUpdated → агрегат зоны → DynamicPriceUpdated`. Это позволяет видеть не только здоровье Flink как платформы, но и фактическую задержку бизнес-вычисления.

## 5. Метрики доставки Outbox → Kafka

Для каждого доменного сервиса:

- количество записей в `outbox`, ещё не опубликованных в Kafka;
- возраст самой старой непереданной записи;
- скорость появления записей `outbox`;
- скорость публикации Debezium;
- состояние соединителя Kafka Connect;
- отставание CDC;
- количество перезапусков соединителя;
- количество ошибок публикации;
- количество сообщений, ушедших в повторную обработку или DLQ.

Ключевой сигнал деградации — рост возраста самой старой записи `outbox`. Даже при работающем сервисе это означает, что остальные домены получают устаревшее состояние.

## 6. Метрики потребителей

Для каждого потребителя Kafka:

- скорость получения событий;
- скорость успешной обработки;
- длительность обработки p50/p95/p99;
- количество ошибок по типам;
- число повторных попыток;
- число сообщений в DLQ;
- число повторов, отфильтрованных Inbox;
- возраст самого старого ожидающего события;
- количество ошибок несовместимой схемы.

Для Payments и Booking любое сообщение в DLQ должно разбираться отдельно, поскольку оно может означать незавершённую поездку или финансовую операцию.

## 7. Метрики Saga

Для процесса поездки собираются:

- число активных Saga;
- число новых Saga в секунду;
- число успешно завершённых Saga;
- число отменённых Saga;
- число завершившихся ошибкой Saga;
- длительность Saga p50/p95/p99;
- длительность каждого шага;
- число тайм-аутов на каждом шаге;
- количество выполненных компенсаций;
- количество Saga без изменения состояния дольше установленного срока;
- время от `BookingCreated` до `BookingConfirmed`;
- время поиска водителя;
- время авторизации платежа;
- число повторных команд, остановленных идемпотентностью.

В Grafana должна быть возможность перейти от агрегированной метрики к конкретному `saga_id`, затем найти связанные журналы в Loki и трассу в Jaeger.

## 8. Бизнес-метрики реального времени

Технически исправная Kafka ещё не означает, что система решает задачу бизнеса. Поэтому рядом с техническими показателями отображаются:

- количество создаваемых заказов по регионам и зонам;
- количество активных поездок;
- количество доступных водителей;
- отношение спроса к предложению по зоне;
- медианное и p95 время назначения водителя;
- доля заказов, где водитель не найден до истечения срока;
- текущий динамический коэффициент по зонам;
- частота пересчёта динамической цены;
- количество рекомендаций по перераспределению водителей;
- доля отклонений Fraud;
- доля неуспешных авторизаций и списаний.

## 9. Основные оповещения

Минимальный набор правил:

| Сигнал | Условие | Реакция |
|---|---|---|
| Недоступная партиция Kafka | `offline partitions > 0` | Критическое оповещение SRE |
| Неполная репликация | Сохраняется дольше допустимого периода | Оповещение SRE, проверка брокеров/дисков |
| Рост отставания критичного потребителя | Отставание растёт и превышает допустимое время доставки | SRE + команда-владелец потребителя |
| Outbox не выгружается | Возраст старейшей записи растёт | Команда домена + платформенная команда |
| Kafka Connect/Debezium остановлен | Соединитель не в состоянии RUNNING | Платформенная команда |
| Flink job остановлен | Задание не RUNNING | Data/SRE |
| Контрольные точки Flink неуспешны | Несколько последовательных ошибок | Data/SRE |
| DLQ Payments/Booking не пуст | Появилось новое сообщение | Немедленный разбор владельцем домена |
| Saga зависла | Нет перехода состояния дольше срока шага | Booking/SRE |
| Рост компенсаций Saga | Существенное отклонение от обычного уровня | Booking + зависимый домен |

Числовые пороги по задержкам и отставанию не фиксируются «на глаз». Их нужно получить из нагрузочных испытаний и затем привязать к целевым показателям доступности и времени реакции системы.

## 10. Панели Grafana

Для эксплуатации достаточно пяти основных панелей:

1. **Обзор событийной платформы** — регионы, брокеры, входящий поток, недоступные партиции, DLQ.
2. **Потребители Kafka** — отставание по группам, топикам и регионам.
3. **Flink в реальном времени** — состояние заданий, обратное давление, контрольные точки, задержка вычислений.
4. **Saga поездки** — активные процессы, длительность, ошибки, компенсации и зависшие Saga.
5. **Доставка событий** — Outbox, Debezium, Kafka Connect, повторы и DLQ.

Такое разделение позволяет SRE сначала увидеть проблему на общей панели, а затем быстро перейти к конкретному уровню: брокер, потребитель, потоковое задание, Saga или доставка события из базы.
