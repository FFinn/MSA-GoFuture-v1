# ADR-002: Событийно-ориентированная архитектура GoFuture

**Статус:** На рассмотрении  
**Автор:** Александр Вафин  
**Заинтересованные стороны:** команды Booking, Driver, Pricing, Payments, Notification, Geography, Analytics и Fraud; платформенная команда; SRE-команда; инженеры данных; архитектурный комитет  
**Дата:** 2026-09-15

---

## 1. Контекст

После разделения монолита на доменные сервисы одной декомпозиции недостаточно для целевой нагрузки. При более чем 500 тысячах одновременно выполняемых поездок наиболее частые изменения — координаты водителей, изменение спроса и предложения, расчёт цены, подбор водителя, проверки мошенничества и переходы состояния поездки — не должны образовывать длинную цепочку синхронных HTTP-вызовов.

Такая цепочка создаёт две проблемы. Во-первых, отказ или замедление одного сервиса начинает распространяться на остальные. Во-вторых, данные, необходимые для динамического ценообразования и перераспределения водителей, приходят с высокой частотой и должны обрабатываться непрерывным потоком, а не периодическими заданиями Celery.

В текущем ландшафте уже есть RabbitMQ и Celery. Они могут временно сохраняться для внутренних фоновых задач отдельных сервисов, но не используются как целевой механизм междоменного обмена и поэтому не показаны на C2 событийной платформы. Для междоменных событий вводится Apache Kafka.

Для потоковых вычислений выбирается Apache Flink. Он уже используется инженерами данных GoFuture и подходит для вычислений с состоянием: оценки спроса и предложения по зонам, подготовки сигналов для динамического ценообразования, формирования рекомендаций по перераспределению водителей и потоковых признаков для Fraud.

Для процесса поездки нужна Saga. Процесс долгоживущий, содержит ветвления, сроки ожидания и компенсации, поэтому хореография без явного координатора сделала бы его трудно наблюдаемым. Оркестрация размещается в домене Booking, который владеет жизненным циклом поездки.

## 2. Требования

### 2.1. Функциональные требования

| № | Требование |
|---|---|
| **ФТ-01** | Доменные сервисы должны публиковать факты изменения состояния в виде доменных событий. |
| **ФТ-02** | Платформа должна обрабатывать события `BookingCreated`, `DriverLocationUpdated` и другие события поездки в реальном времени. |
| **ФТ-03** | События должны разделяться по регионам так, чтобы нагрузка одного региона не блокировала обработку другого. |

| **ФТ-05** | Потоковая обработка должна формировать сигналы перераспределения водителей между зонами и передавать их в Geography. |
| **ФТ-06** | Процесс создания и выполнения поездки должен координироваться Saga с поддержкой сроков ожидания, повторов и компенсаций. |
| **ФТ-07** | Analytics должен получать поток доменных событий без прямого чтения рабочих таблиц других сервисов. |
| **ФТ-08** | При временном сбое потребителя событие не должно теряться и должно быть обработано после восстановления. |
| **ФТ-09** | Повторная доставка одного события не должна приводить к повторному списанию, созданию второй поездки или другой повторной бизнес-операции. |
| **ФТ-10** | Для ошибочных сообщений должен существовать отдельный маршрут повторной обработки и топик недоставленных сообщений. |

## 3. Решение

### 3.1. Общий подход

Междоменные изменения передаются через Apache Kafka как неизменяемые события. Kafka становится транспортом и журналом доменных событий, но не заменяет базы данных сервисов: источником истины для каждого домена остаётся собственная база PostgreSQL или специализированное хранилище домена.

У решения четыре основных контура:

1. **Доменные сервисы** — Booking, Driver, Pricing, Payments, Notification, Geography, Analytics и Fraud.
2. **Apache Kafka** — региональные журналы событий и команд.
3. **Apache Flink** — потоковые вычисления с состоянием.
4. **Контур наблюдаемости** — Prometheus, Grafana, Alertmanager, Loki, OpenTelemetry и Jaeger.

Каждый домен сохраняет собственную базу PostgreSQL. На диаграмме C2 базы показаны раздельно, чтобы не создавать впечатление общей базы после декомпозиции.

Исходный файл диаграммы: [`C2-event-platform.puml`](./C2-event-platform.puml).

### 3.2. Формат доменного события

Каждое событие содержит общий заголовок и полезную нагрузку конкретного типа.

```json
{
  "event_id": "uuid",
  "event_type": "BookingCreated",
  "event_version": 1,
  "occurred_at": "2026-09-15T12:00:00Z",
  "region_id": "<region>",
  "aggregate_type": "booking",
  "aggregate_id": "booking-123",
  "correlation_id": "uuid",
  "causation_id": "uuid",
  "saga_id": "uuid-or-null",
  "trace_id": "trace-id",
  "payload": {}
}
```

`correlation_id` связывает сообщения одного пользовательского действия, `causation_id` показывает, какое сообщение стало непосредственной причиной текущего, а `saga_id` связывает шаги одной Saga. `event_id` используется для защиты потребителей от повторной обработки.

Схемы событий хранятся в реестре схем. Клиенты Kafka используют реестр при сериализации и чтении сообщений. Сам брокер Kafka не отвечает за смысловую проверку схем. Для уже опубликованной версии запрещается изменение смысла существующего поля. Несовместимое изменение оформляется новой версией события.

### 3.3. Доменные границы событий

Потоковая платформа не должна становиться новым владельцем бизнес-логики. Flink вычисляет **сигналы**, а окончательное доменное решение принимает соответствующий сервис.

Например, Flink рассчитывает `DemandSupplySignalCalculated`, но именно Pricing на основании этого сигнала меняет динамический коэффициент и публикует `DynamicPriceUpdated`. Аналогично Flink формирует `DriverRedistributionSignalCalculated`, а Geography принимает решение и публикует `DriverRedistributionSuggested`.

Сохраняются ранее определённые границы:

- **Driver** отвечает за доступность и атомарное резервирование водителя;
- **Geography** отвечает за координаты, геопоиск и поиск подходящих кандидатов;
- **Booking** связывает выбранного и зарезервированного водителя с конкретной поездкой;
- **Pricing** владеет тарифами и окончательным расчётом цены;
- **Payments** владеет финансовым состоянием;
- **Fraud** владеет решением о риске.

### 3.4. Основные доменные события

| Домен | События | Для чего используются |
|---|---|---|
| **Booking** | `BookingCreated`, `DriverAssigned`, `BookingConfirmed`, `BookingCancelled`, `TripStarted`, `TripCompleted`, `BookingCompleted` | Жизненный цикл заказа и поездки |
| **Driver** | `DriverAvailabilityChanged`, `DriverReserved`, `DriverReservationRejected`, `DriverReleased` | Доступность и исключение двойного назначения водителя |
| **Geography** | `DriverLocationUpdated`, `DriverMatched`, `DriverNotFound`, `DriverRedistributionSuggested` | Координаты, поиск кандидата и перераспределение водителей |
| **Pricing** | `PriceQuoteCalculated`, `PriceQuoteExpired`, `DynamicPriceUpdated` | Расчёт и изменение цены |
| **Payments** | `PaymentAuthorized`, `PaymentAuthorizationFailed`, `PaymentAuthorizationReleased`, `PaymentCaptured`, `PaymentCaptureFailed` | Авторизация, списание и отмена финансовых операций |
| **Fraud** | `FraudCheckPassed`, `FraudCheckRejected` | Результат проверки риска |
| **Notification** | `NotificationSent`, `NotificationFailed` | Результат доставки уведомления |
| **Analytics** | Собственных событий минимум; сервис в основном потребляет события других доменов | Построение аналитических проекций |

Событие описывает уже произошедший факт и не формулируется как просьба выполнить действие. Команды Saga передаются отдельно, например `PriceQuoteRequested`, `FraudCheckRequested`, `DriverMatchingRequested`, `DriverReservationRequested`, `PaymentAuthorizationRequested`.

### 3.5. Региональное разделение и схема топиков Kafka

Требование «партиционирование по регионам» реализуется в два уровня.

**Регион — верхняя граница разделения потока.** Для каждого региона используется собственный набор топиков вида `gofuture.<region>...`. Это означает, что поток сначала разделяется по региону, а высокочастотные координаты и события поездок не смешиваются между удалёнными регионами.

**Kafka-партиция внутри региона определяется ключом агрегата.** После выбора регионального топика событие попадает в одну из его партиций по `booking_id`, `driver_id`, `payment_id`, `zone_id` или другому идентификатору владельца порядка. Так регионы остаются изолированными, а события одного агрегата сохраняют порядок.

Одна Kafka-партиция на целый регион сознательно не используется: это превратило бы регион в последовательную очередь и ограничило горизонтальное масштабирование.

| Топик | Ключ Kafka-партиции | Производитель | Основные потребители |
|---|---|---|---|
| `gofuture.<region>.booking.events.v1` | `booking_id` | Booking | Fraud, Payments, Notification, Analytics, Flink |
| `gofuture.<region>.driver.location.v1` | `driver_id` | Geography | Flink, Analytics |
| `gofuture.<region>.driver.events.v1` | `driver_id` | Driver | Booking, Geography, Analytics |
| `gofuture.<region>.geography.matching.events.v1` | `booking_id` | Geography | Booking, Driver, Analytics |
| `gofuture.<region>.geography.zone.events.v1` | `zone_id` | Geography | Driver, Analytics, Flink |
| `gofuture.<region>.pricing.quote.events.v1` | `booking_id` | Pricing | Booking, Analytics |
| `gofuture.<region>.pricing.zone.events.v1` | `zone_id` | Pricing | Booking, Analytics |
| `gofuture.<region>.payments.events.v1` | `payment_id` | Payments | Booking, Fraud, Notification, Analytics |
| `gofuture.<region>.fraud.events.v1` | `booking_id` | Fraud | Booking, Payments, Analytics |
| `gofuture.<region>.notification.events.v1` | `notification_id` | Notification | Analytics |
| `gofuture.<region>.stream.zone-signals.v1` | `zone_id` | Flink | Pricing, Geography |
| `gofuture.<region>.stream.booking-signals.v1` | `booking_id` | Flink | Fraud |
| `gofuture.<region>.<domain>.commands.v1` | идентификатор целевого агрегата | Оркестратор Booking | Соответствующий доменный сервис |

Количество Kafka-партиций заранее не фиксируется произвольным числом. В условии нет данных о количестве событий в секунду, среднем размере сообщения и подтверждённой пропускной способности одной партиции. Поэтому число партиций определяется нагрузочными испытаниями по формуле:

`требуемая пиковая скорость потока / измеренная безопасная производительность одной партиции + резерв на рост`.

Отдельно измеряется `driver.location`, потому что координаты водителей формируют самый частый поток. Полученные значения фиксируются в эксплуатационной конфигурации Kafka и пересматриваются при росте нагрузки.

Для каждого рабочего топика предусматривается связанный топик повторной обработки и топик недоставленных сообщений. Например:

- `gofuture.<region>.payments.events.retry.v1`;
- `gofuture.<region>.payments.events.dlq.v1`.

В топик недоставленных сообщений добавляются исходный топик, номер партиции, смещение, идентификатор события, код ошибки и время последней попытки. Это позволяет повторно обработать сообщение после исправления причины ошибки.

### 3.6. Потоковая обработка Apache Flink

Flink используется там, где нужны вычисления над непрерывным потоком и состояние между событиями. Для доменных событий, не требующих потоковых вычислений, используются обычные группы потребителей Kafka.

Основные задания Flink:

1. **Спрос и предложение по зонам.** Потоки `BookingCreated`, `BookingCancelled`, `TripStarted`, `TripCompleted`, `DriverLocationUpdated` и `DriverAvailabilityChanged` агрегируются по `region_id + zone_id` во временных окнах.
2. **Сигнал динамической цены.** На основании количества активных заказов, свободных водителей, скорости появления новых заказов и времени назначения водителя формируется `DemandSupplySignalCalculated`. Pricing использует его как один из входов для расчёта цены и при изменении коэффициента публикует `DynamicPriceUpdated`.
3. **Сигнал перераспределения водителей.** Flink выявляет зоны с ожидаемым дефицитом или профицитом водителей и публикует `DriverRedistributionSignalCalculated`. Geography принимает решение о применении рекомендации и публикует `DriverRedistributionSuggested`.
4. **Потоковые признаки для Fraud.** Из поездок, платежей и поведения пользователя формируются короткоживущие агрегаты `FraudFeaturesCalculated`, которые Fraud использует при оценке риска.
5. **Подготовка потока для Analytics.** Потоки обогащаются служебными измерениями и поступают в аналитический контур без прямого чтения рабочих баз.

Flink хранит состояние вычислений в контрольных точках. После сбоя задание восстанавливается с последней успешной контрольной точки и продолжает чтение Kafka без полного пересчёта потока.

### 3.7. Почему выбран Flink

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **Apache Flink** | Низкая задержка, вычисления с состоянием, временные окна, контрольные точки, уже используется инженерами данных GoFuture | Требует отдельного кластера и компетенций эксплуатации | **Выбран** |
| **Kafka Streams** | Простая интеграция с Kafka, хорошая модель локального состояния | Библиотека ориентирована на JVM; основной прикладной стек GoFuture — Python | Не выбран как основной инструмент |
| **Spark Structured Streaming** | Уже знаком команде данных, удобен для тяжёлой аналитики | Для наиболее чувствительных к задержке расчётов менее удобен, чем Flink | Остаётся для пакетной и менее срочной аналитики |

### 3.8. Saga поездки

Выбрана **оркестрационная Saga с итоговой согласованностью**. Независимые ранние шаги могут выполняться параллельно, но переходы процесса и компенсации контролирует Booking.

Оркестратор координирует только жизненный цикл поездки, потому что именно Booking владеет этим процессом.

| Шаг | Команда | Успешное событие | Ошибка / компенсация |
|---|---|---|---|
| **1** | — | `BookingCreated` | Начало Saga |
| **2А** | `PriceQuoteRequested` | `PriceQuoteCalculated` | Если цену рассчитать нельзя — `BookingCancelled` |
| **2Б** | `FraudCheckRequested` | `FraudCheckPassed` | `FraudCheckRejected` → завершить Saga отказом |
| **3** | `DriverMatchingRequested` | `DriverMatched` | `DriverNotFound` → повторять до срока ожидания, затем `BookingCancelled` |
| **4** | `DriverReservationRequested` | `DriverReserved` | `DriverReservationRejected` → запросить следующего кандидата; после истечения срока — `BookingCancelled` |
| **5** | `PaymentAuthorizationRequested` | `PaymentAuthorized` | `PaymentAuthorizationFailed` → `DriverReleaseRequested` + `BookingCancelled` |
| **6** | — | `DriverAssigned`, затем `BookingConfirmed` | Поездка готова к выполнению |
| **7** | — | `TripStarted` | Отмена после старта обрабатывается отдельным бизнес-правилом |
| **8** | — | `TripCompleted` | Необратимая точка: поездку уже нельзя отменить как несостоявшуюся |
| **9** | `PaymentCaptureRequested` | `PaymentCaptured` | При временной ошибке — повторять; завершённая поездка не отменяется из-за ошибки списания |
| **10** | — | `BookingCompleted` | Saga завершена |

Шаги 2А и 2Б выполняются параллельно: расчёт цены и проверка риска независимы. Это уменьшает время до начала поиска водителя.

Если котировка цены истекла до подтверждения поездки, Booking повторяет `PriceQuoteRequested` перед переходом к `BookingConfirmed`.

Geography может найти подходящего кандидата, но только Driver атомарно резервирует его. Это защищает от ситуации, когда два параллельных заказа одновременно выбрали одного свободного водителя.

До `TripStarted` возможны компенсации:

- освобождение зарезервированного водителя — `DriverReleaseRequested` → `DriverReleased`;
- снятие авторизации платежа — `PaymentAuthorizationReleaseRequested` → `PaymentAuthorizationReleased`;
- завершение заказа — `BookingCancelled`.

`TripCompleted` является необратимой точкой. После неё проблемы со списанием решаются повторными попытками и отдельным процессом финансового урегулирования, а не отменой уже совершённой поездки.

### 3.9. Путь команды Saga через событийную платформу

Команды Saga публикуются через тот же надёжный механизм, что и доменные события:

1. Booking меняет состояние Saga и записывает команду, например `PaymentAuthorizationRequested`, в собственный транзакционный исходящий журнал в одной локальной транзакции.
2. Debezium читает эту запись из журнала изменений базы PostgreSQL домена Booking.
3. Kafka Connect публикует команду в региональный топик `gofuture.<region>.payments.commands.v1`.
4. Payments получает команду как потребитель своей группы.
5. Результат (`PaymentAuthorized` или `PaymentAuthorizationFailed`) Payments записывает в собственный исходящий журнал.
6. Debezium публикует результат в `gofuture.<region>.payments.events.v1`.
7. Booking получает событие и переводит Saga на следующий шаг.

### 3.10. Почему не выбрана хореография Saga

Хореография была бы проще для короткой линейной цепочки, но у поездки быстро появляются ветвления: истечение котировки цены, отсутствие водителя, конфликт резервирования, отказ Fraud, ошибка авторизации платежа, отмена пассажиром, срок ожидания и компенсации. При хореографии правило перехода распределилось бы по нескольким сервисам, а восстановление зависшей Saga потребовало бы собирать её состояние по журналам.

Оркестрация делает состояние процесса явным, позволяет хранить срок выполнения каждого шага и даёт единую точку ответа на вопрос, почему конкретная поездка не перешла дальше.

### 3.11. Надёжная доставка

Для доменных сервисов используется **транзакционный исходящий журнал + захват изменений данных**.

1. Сервис изменяет доменную модель и добавляет запись в таблицу `outbox` в одной локальной транзакции базы PostgreSQL.
2. Kafka Connect с Debezium читает журнал изменений PostgreSQL и публикует запись `outbox` в Kafka.
3. После публикации событие становится доступно группам потребителей.
4. Потребитель перед изменением своей модели проверяет `event_id` в собственном реестре обработанных событий (`inbox`).
5. Доменное изменение и запись `event_id` выполняются в одной локальной транзакции.
6. Смещение Kafka подтверждается после успешной локальной транзакции.

Так устраняется двойная запись «сначала база, потом Kafka». Если приложение завершится после фиксации бизнес-транзакции, Debezium всё равно увидит запись `outbox`. Если потребитель обработал событие, но завершился до подтверждения смещения, Kafka доставит событие повторно, а `inbox` не позволит выполнить бизнес-операцию второй раз.

Гарантия на уровне доменных сервисов формулируется как **доставка не менее одного раза + идемпотентная обработка**. Сквозная гарантия «ровно один раз» не используется, поскольку бизнес-процесс включает внешние платёжные, картографические и другие системы.

Для Kafka применяются дополнительные меры:

- коэффициент репликации критичных топиков — не менее 3;
- `min.insync.replicas = 2`;
- подтверждение продюсера — `acks=all`;
- идемпотентный продюсер там, где сообщения пишутся напрямую, а не через Debezium;
- порядок событий агрегата обеспечивается неизменным ключом Kafka-партиции;
- автоматическая фиксация смещений потребителя отключена;
- временные ошибки уходят в топики повторной обработки с увеличивающейся задержкой;
- неисправимые сообщения после ограниченного числа попыток уходят в топик недоставленных сообщений;
- схемы проверяются на совместимость до публикации новой версии сервиса;
- для Flink включены контрольные точки и восстановление состояния;
- внешние вызовы Payments и Notification получают собственный ключ идемпотентности.

### 3.12. Повторная обработка

Используется три уровня:

1. короткие локальные повторы для кратковременной ошибки;
2. отдельный топик повторной обработки для ошибок, которые требуют паузы;
3. топик недоставленных сообщений для сообщений, которые не удалось обработать после установленного числа попыток.

Возврат сообщения из топика недоставленных сообщений выполняется только после устранения причины и с сохранением исходного `event_id`. Поэтому повторная подача безопасна для идемпотентного потребителя.

## 4. Мониторинг и наблюдаемость

Подробный перечень инструментов, метрик и правил вынесен в [`monitoring.md`](./monitoring.md).

### 4.1. Подход

Для прикладных сервисов используется метод **RED**:

- **Rate** — скорость запросов и событий;
- **Errors** — доля ошибок;
- **Duration** — длительность обработки.

Для Kafka и Flink дополнительно контролируются состояние репликации, отставание групп потребителей, контрольные точки, обратное давление и возраст необработанных сообщений.

Для Saga отдельно собираются бизнес-технические метрики: количество активных процессов, длительность Saga, число превышений срока, компенсаций и зависших процессов.

### 4.2. Инструменты

| Инструмент | Назначение |
|---|---|
| **Prometheus** | Сбор числовых метрик сервисов, Kafka, Flink, Kafka Connect/Debezium и Saga |
| **Grafana** | Панели по регионам, топикам, группам потребителей, потоковым заданиям и Saga |
| **Alertmanager** | Оповещения по нарушению целевых показателей и техническим отказам |
| **Loki** | Централизованные журналы приложений, Kafka Connect, Flink и потребителей |
| **Kafka Exporter + JMX Exporter** | Метрики брокеров, партиций и групп потребителей Kafka |
| **Flink Prometheus Reporter** | Публикация метрик заданий Flink для сбора Prometheus |
| **OpenTelemetry Collector + Jaeger** | Распределённая трассировка по `trace_id`, `correlation_id` и `saga_id` |
| **PostgreSQL Exporter** | Метрики каждой доменной базы PostgreSQL |

Все доменные сервисы передают журналы в Loki и трассы в OpenTelemetry Collector. На C2 отдельные связи частично сокращены для читаемости, что отмечено на самой диаграмме.

### 4.3. Критические группы метрик

**Kafka**

- входящая и исходящая скорость сообщений;
- количество недоступных партиций;
- количество партиций с неполным числом синхронных реплик;
- число изменений состава ISR;
- использование диска брокеров;
- задержка обработки запросов брокером;
- отставание каждой группы потребителей по региону и партиции;
- количество перебалансировок групп потребителей.

**Потребители**

- скорость обработки событий;
- длительность обработки p50/p95/p99;
- количество ошибок;
- число повторных попыток;
- количество сообщений в топике недоставленных сообщений;
- возраст самого старого необработанного сообщения.

**Flink**

- состояние задания;
- количество входящих и исходящих записей;
- длительность и результат контрольных точек;
- время с последней успешной контрольной точки;
- количество перезапусков;
- размер состояния;
- обратное давление операторов;
- отставание водяных знаков относительно текущего времени.

**Исходящий журнал / Debezium / Kafka Connect**

- количество непереданных записей `outbox`;
- возраст самой старой непереданной записи;
- состояние соединителя;
- отставание захвата изменений данных;
- количество ошибок публикации.

**Saga**

- количество активных Saga;
- число успешных, отменённых и ошибочных Saga;
- длительность p50/p95/p99;
- число превышений срока по шагам;
- число выполненных компенсаций;
- количество Saga, не изменявшихся дольше допустимого срока;
- время назначения водителя;
- время от `BookingCreated` до `BookingConfirmed`.

**Бизнес-сигналы реального времени**

- скорость `BookingCreated` по регионам и зонам;
- скорость `DriverLocationUpdated`;
- отношение спроса к числу доступных водителей по зоне;
- доля заказов без найденного водителя;
- частота изменения динамического коэффициента;
- количество отклонений Fraud;
- доля неуспешных авторизаций и списаний.

## 5. Альтернативы

### 5.1. Оставить RabbitMQ основным средством междоменного обмена

**Плюсы:** технология уже используется, команда знакома с эксплуатацией.

**Минусы:** основная модель RabbitMQ ориентирована на доставку сообщений потребителю, а не на долговременный журнал событий с большим числом независимых читателей и повторным воспроизведением истории. Для потоковой аналитики и восстановления проекций Kafka подходит лучше.

**Решение:** RabbitMQ остаётся для части внутренних фоновых задач, а доменные события передаются через Kafka.

### 5.2. Писать событие в Kafka напрямую после изменения базы

**Плюсы:** меньше компонентов.

**Минусы:** возникает окно между фиксацией транзакции в базе PostgreSQL и публикацией сообщения. Сбой в этом окне приводит к изменённым данным без соответствующего события.

**Решение:** использовать транзакционный исходящий журнал и Debezium.

### 5.3. Использовать хореографическую Saga

**Плюсы:** нет отдельного координатора процесса.

**Минусы:** ветвления, сроки ожидания и компенсации поездки распределяются между несколькими сервисами; трудно определить текущее состояние конкретной Saga и безопасно восстановить её после сбоя.

**Решение:** использовать оркестрацию в Booking.

### 5.4. Сделать одну Kafka-партицию на регион

**Плюсы:** простое сохранение порядка внутри региона.

**Минусы:** регион превращается в одну последовательную очередь и быстро становится ограничением производительности.

**Решение:** регион является верхней границей разделения потока через отдельный набор топиков, а внутри региона используется несколько Kafka-партиций по ключам агрегатов.

## 6. Компромиссы и риски

1. **Система становится сложнее в эксплуатации.**  
   *Меры:* единые шаблоны топиков и событий, автоматизированное создание топиков, общие панели Grafana, стандартные оповещения и обязательные проверки схем в конвейере сборки.

2. **Большой поток координат водителей может занять существенный объём Kafka.**  
   *Меры:* отдельный топик `driver.location`, короткий срок хранения по сравнению с бизнес-событиями, отдельный расчёт числа партиций и нагрузочные испытания.

3. **Неверно выбранный ключ создаст горячую Kafka-партицию.**  
   *Меры:* не смешивать в одном топике события с разными владельцами порядка; для поездки использовать `booking_id`, для водителя — `driver_id`, для зоны — `zone_id`, для платежа — `payment_id`.

4. **Повторная доставка может привести к повторным бизнес-операциям.**  
   *Меры:* уникальный `event_id`, реестр обработанных событий, ключи идемпотентности внешних операций и фиксация смещения только после локальной транзакции.

5. **Saga может зависнуть между шагами.**  
   *Меры:* хранить состояние и срок выполнения каждого шага в Booking, контролировать сроки, публиковать метрики активных и зависших Saga, выполнять компенсацию там, где она допустима.

6. **Несовместимое изменение события сломает несколько команд одновременно.**  
   *Меры:* реестр схем, обратная совместимость по умолчанию, отдельная версия при несовместимом изменении и проверка контракта в конвейере сборки.

7. **Flink становится отдельной критической платформой.**  
   *Меры:* контрольные точки, автоматический перезапуск, отдельный мониторинг обратного давления и времени контрольных точек, возможность восстановить состояние из Kafka.
