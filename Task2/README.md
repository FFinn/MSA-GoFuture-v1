# Задание 2. Проектируем событийно-ориентированную архитектуру

В этом задании спроектирована событийная платформа GoFuture для обработки более 500 тысяч одновременно выполняемых поездок, динамического ценообразования и потоковой обработки данных в реальном времени.

## Артефакты

- [`ADR-002-event-driven-architecture.md`](./ADR-002-event-driven-architecture.md) — модель доменных событий, региональная схема топиков Kafka, ключи партиционирования, Apache Flink, Saga поездки, механизмы надёжной доставки, альтернативы и риски.
- [`C2-event-platform.puml`](./C2-event-platform.puml) — C2-диаграмма событийной платформы с отдельными доменными базами PostgreSQL, Kafka, Flink, Debezium и средствами наблюдаемости.
- [`monitoring.md`](./monitoring.md) — подход к мониторингу, список инструментов, метрики Kafka, Flink, исходящего журнала и Saga, а также основные оповещения.

## Основные решения

Доменные события передаются через Apache Kafka. **Регион является верхней границей разделения потока:** для каждого региона используется собственный набор топиков вида `gofuture.<region>...`. Внутри регионального топика Kafka-партиция выбирается по ключу конкретного агрегата — `booking_id`, `driver_id`, `payment_id` или `zone_id`. Так региональные потоки изолированы, а порядок событий одного агрегата сохраняется без превращения всего региона в одну последовательную очередь.

Потоки с разными правилами упорядочивания разведены по отдельным топикам. Например, события подбора водителя используют `geography.matching.events` с ключом `booking_id`, а зональные события — `geography.zone.events` с ключом `zone_id`. Для Pricing отдельно разделены котировки конкретной поездки и зональные коэффициенты.

Количество Kafka-партиций определяется по результатам нагрузочных испытаний на основании пиковой скорости событий и измеренной безопасной производительности одной партиции. Высокочастотный поток `driver.location` рассчитывается отдельно.

Для вычислений над непрерывным потоком выбран Apache Flink. Он рассчитывает спрос и предложение по зонам и формирует сигналы для динамического ценообразования, перераспределения водителей и Fraud. Окончательное бизнес-решение остаётся за соответствующим доменным сервисом.

Процесс поездки реализуется как оркестрационная Saga с итоговой согласованностью. Состояние Saga принадлежит Booking. Расчёт цены и проверка Fraud выполняются параллельно, далее координируются поиск кандидата, атомарное резервирование водителя, авторизация платежа, выполнение поездки и окончательное списание.

Команды Saga публикуются через тот же механизм, что и доменные события: Booking сохраняет команду в транзакционный исходящий журнал, Debezium через Kafka Connect публикует её в Kafka, целевой сервис обрабатывает команду и возвращает результат своим доменным событием.

Надёжная доставка строится на транзакционном исходящем журнале, захвате изменений данных и реестре обработанных событий. Потребители работают идемпотентно. Сквозная гарантия формулируется как «доставка не менее одного раза + идемпотентность»; гарантия «ровно один раз» не заявляется для процесса, в котором участвуют внешние системы.

RabbitMQ и Celery могут временно оставаться внутри отдельных сервисов для фоновых задач, но не входят в целевую междоменную событийную платформу и поэтому не показаны на C2.

Мониторинг построен на Prometheus, Grafana, Alertmanager и Loki с добавлением Kafka/JMX Exporter, Flink Prometheus Reporter, PostgreSQL Exporter, OpenTelemetry и Jaeger. Все доменные сервисы передают журналы и распределённые трассы в общий контур наблюдаемости.
