# Задание 1. Проектируем домены

В этом задании описан поэтапный переход GoFuture от монолита к восьми доменным сервисам, соответствующим продуктовым командам.

## Артефакты

- [`ADR-001-domain-decomposition.md`](./ADR-001-domain-decomposition.md) — нефункциональные требования, карта доменов, очерёдность выделения сервисов, целевая C2-диаграмма переходного периода, механизм обратной совместимости, план миграции данных, альтернативы и риски.
- [`C2-to-be.puml`](./C2-to-be.puml) — C2-диаграмма архитектуры периода поэтапной декомпозиции с доменными сервисами, отдельными хранилищами, шлюзом программного интерфейса, ACL и явно выделенным временным переходным контуром.

## Порядок решения

Материалы расположены в том же порядке, что и этапы задания:

1. нефункциональные требования;
2. карта сервисов и доменные границы;
3. приоритетная очерёдность выделения сервисов;
4. целевая C2-диаграмма периода поэтапной декомпозиции;
5. механизм обратной совместимости;
6. план миграции данных каждого сервиса.

## Основные решения

Декомпозиция выполняется постепенно, без общей остановки платформы. Внешние клиенты продолжают работать через единую входную точку. Шлюз программного интерфейса и ACL направляют уже перенесённые операции в доменные сервисы, а оставшиеся — в монолит.

У каждого выделенного сервиса появляется собственное хранилище и право владения своими данными. Прямые обращения к базам и оперативным хранилищам других сервисов запрещены. Redis для Driver, Pricing и Geography показан как отдельные логические хранилища; даже при размещении в одном физическом кластере домены не читают ключи друг друга.

Граница Driver / Geography / Booking определена отдельно: Driver решает, может ли водитель принимать заказы; Geography находит и ранжирует подходящих кандидатов; Booking назначает выбранного водителя на конкретную поездку.

Для переноса больших объёмов используется первоначальная пакетная загрузка, затем захват изменений данных и поэтапное переключение трафика после сверки. До передачи владения записью маршрут можно быстро вернуть на монолит. После передачи владения данными возврат выполняется только через управляемую обратную миграцию.

Порядок выделения: Notification → Geography → Pricing и Analytics → Driver → Booking → Fraud → Payments. Fraud выделяется после стабилизации Booking и фиксации контракта финансовых операций через слой обратной совместимости. Payments переносится последним из-за максимальной цены ошибки и необходимости строгой финансовой сверки.

## Выбор веб-фреймворка

Декомпозиция монолита не требует одновременной смены Python-фреймворка. На первом этапе доменные сервисы сохраняют **Django**, который уже используется в GoFuture и знаком командам разработки. Это позволяет не совмещать архитектурную миграцию с переписыванием прикладного кода и не увеличивать риск годовой программы декомпозиции.

Микросервисная архитектура в этом решении определяется независимыми доменными границами, отдельным владением данными, самостоятельным развёртыванием и масштабированием сервисов, а не выбором конкретного веб-фреймворка. Поэтому переход с Django на FastAPI сам по себе не является необходимым условием декомпозиции.

Если для отдельного нового сервиса появятся требования, которые Django покрывает хуже — например, специализированный высокочастотный программный интерфейс с иным профилем нагрузки, — выбор FastAPI может быть принят отдельным архитектурным решением. Массовая замена Django на FastAPI в рамках текущей декомпозиции не выполняется.
